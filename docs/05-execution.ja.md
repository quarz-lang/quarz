# 実行モデル: インタプリタと AOT コンパイラ

Quarz は 1 つのフロントエンドと 1 つのランタイムを、2 つのバックエンド(QIR のインタプリタと機械語)で共有します。開発中は `quarz run` で起動の速さと REPL を、本番は `quarz build` で実行速度を取り、**両者の観測可能な挙動は同一**です。

```
                    ┌────────────┐   ┌──────────────┐   ┌───────────────┐
  foo.qz ─────────▶ │ 字句・構文 │─▶ │ 名前解決・型 │─▶ │  QIR(型付き  │
  (+ require 先)    │   解析     │   │   検査       │   │   中間表現)   │
                    └────────────┘   └──────────────┘   └───────┬───────┘
                                                                 │
                       ┌─────────────────────────────────────────┼─────────────────────┐
                       │ quarz run / repl                        │ quarz build          │
                       ▼                                         ▼                      │
               ┌───────────────┐                     ┌────────────────────┐             │
               │ QIR の        │                     │ 最適化(脱仮想化、 │             │
               │ インタプリタ  │                     │ インライン化、RC   │             │
               │               │                     │ 省略、非ボックス化)│             │
               └───────┬───────┘                     └─────────┬──────────┘             │
                       │                                       ▼                        │
                       │                             ┌────────────────────┐             │
                       │                             │ LLVM IR → 機械語   │             │
                       │                             │ (clang)            │             │
                       │                             └─────────┬──────────┘             │
                       ▼                                       ▼                        │
               ┌──────────────────────────────────────────────────────────┐             │
               │  libquarz ランタイム(参照カウント、スケジューラ、コピー │ ◀───────────┘
               │  オンライトのコレクション、文字列、多倍長整数、IO、      │
               │  チャネル、正規表現)                                    │
               └──────────────────────────────────────────────────────────┘
```

## 1. コマンド

| コマンド | 動作 |
|---|---|
| `quarz run app.qz [args]` | 型検査し、QIR に変換(lowering)して解釈実行する(依存ファイルの型検査結果のキャッシュは*予定*) |
| `quarz repl` | REPL。入力ごとに型検査し、定義を追加できる(再定義は不可、代わりに新しい名前を使う) |
| `quarz check app.qz` | 型検査のみ |
| `quarz build app.qz -o app` | ネイティブ実行ファイルを生成(LLVM で最適化) |
| `quarz ir app.qz` | 全関数の QIR を表示する(変換結果のデバッグ用)。`quarz tokens` と `quarz parse` はトークンと構文木を表示する |
| `quarz test` | `test/**/*_test.qz` を実行(*予定*) |
| `quarz fmt` | 整形(*予定*) |
| `quarz pkg add json` | パッケージ管理。マニフェストは `Quarz.toml`(*予定*) |

## 2. コンパイル単位と分割コンパイル

この節は設計で、まだ何も作っていません。今は、プレリュードと require したライブラリを含むプログラム全体を、実行のたびに検査して QIR に変換します(§9)。

- 1 ファイル = 1 コンパイル単位。各単位の型検査結果から**インターフェースファイル** `.qzi`(クラス・メソッドのシグネチャ、フィールドのレイアウト、定数の型、`extension` の一覧、インライン化候補の小さなメソッドの QIR)が生成されます。
- 依存する単位は `.qzi` だけを読みます。引数型が必須なのはこのためで、本体の変更は(シグネチャが変わらない限り)他の単位の再コンパイルを引き起こしません。
- `quarz build` は最終段でプログラム全体の QIR を集めて、クラス階層解析(CHA)による脱仮想化とクロスモジュールのインライン化を行います。クラスが実行時に作られないため、CHA は完全です。
- 標準ライブラリは事前に `.qzi` + ネイティブ(`libquarz-std`)として配布され、`quarz run` でも最初から機械語で動きます。

## 3. QIR

QIR(Quarz Intermediate Representation)は、両方のバックエンドが入力にする中間表現です。レジスタマシン(レジスタは再代入できる)で、基本ブロックからなり、各ブロックにハンドラのブロックを付けられます。Ruby 風の構文は QIR に落ちる段階で単純化されます。

- メソッド呼び出しは、チェッカーが解決できるところでは解決済みです(呼び出しはメソッドを指し、サブクラスが上書きしていればレシーバのクラスで振り分けます)。解決できなければ実行時に名前で探します。コンストラクタ、手続きの呼び出し、`yield`、`super` には専用の呼び出し種別があります。
- よく使うイテレータ(`Int`・`Array`・リテラルの範囲に対する `times`、`upto`、`each`、`map`、`select` など)のブロックはその場のループに変換し、`break`/`next` はジャンプになります。それ以外のブロックはクロージャで、そこから抜ける `break`/`return` はランタイムを通る状態コードです。小さなメソッドはインライン化します。
- 値はタグ付きです(合併型に別の表現は要りません)。`Int` の演算はあふれを検査し、あふれたら多倍長整数で続けます。
- 参照カウントとタスクの切り替えは、ランタイムとバックエンドが生成するコードが行い、QIR の命令にはなりません。ただし、値を複製せずにムーブする箇所は QIR に書かれます。レジスタの最後の読み出しになるコピーや呼び出しの引数は値をムーブするので(`Take`、呼び出しのムーブされる被演算子)、渡したコレクションも参照は一意のままです。
- 最適化のあと、値が同時に生きることのないレジスタは同じ番号を共有します(参照カウントされる値を持ちうるレジスタとそうでないものは分けます)。インライン化した呼び出し先を含むメソッドでも、レジスタは百ではなく十数で済みます。実行ファイルはコンパイル元の QIR を埋め込むので、フォールバック先のインタプリタともレジスタの対応は一致します。

インタプリタとコンパイラの意味論が一致する根拠は、どちらも同じ QIR を入力にし、同じランタイム関数を呼ぶことです。QIR から先で許される差は性能だけで、CI では同じテストスイートを両モードで実行して差分検査(differential testing)を行います。

## 4. インタプリタ

- **インタプリタは QIR の命令をそのまま実行します**。別のバイトコードはありません。レジスタはタグ付きの値を持ちます。`Int`・`Float`・`Bool` は割り当てられませんが、タグは付いています。頻出の操作(`Int`/`Float` の算術と比較、配列の要素の読み出しと追加、長さ、フィールドの読み書き)には専用の命令があります。
- 型情報があるため、動的言語のインタプリタに必要なインラインキャッシュやガードがありません。目標は Lua/LuaJIT インタプリタ級の速度で、Ruby(YJIT なし)の 3〜10 倍程度を想定しています。
- 将来、ベースライン JIT(QIR → 機械語をその場で生成)を追加できますが、「本番は AOT」を前提にしているため優先度は低く置いています。

## 5. メモリ管理

**参照カウント(RC)+ 一意性によるその場更新 + 可変オブジェクト限定のサイクル回収**を採用します。

今は値を原子的操作なしで参照カウントし、更新は参照が一意でなければコピーします(§9)。以下に書く、共有ビットによる原子的カウント、一般的な再利用、サイクル回収はまだ作っていません。別のスレッドへ値を渡すのはコピーによるだけで(`Task.blocking`)、可変オブジェクトのサイクルは回収されません。

### なぜ参照カウントか

1. **不変値のその場更新**: 参照カウントが 1 の不変値は、「新しい値を返す」操作をその場で破壊的に行えます(Lean 4 / Koka の Perceus)。Quarz の「不変を既定にしつつ速い」はこれに依存しています。
2. **AOT との相性**: トレース GC はネイティブコードのスタックマップ(LLVM statepoint など)か保守的スキャンが必要で、実装の難所です。RC はどちらも不要で、C FFI との境界も単純です。
3. **決定的な解放**: `ensure` と組み合わせて、ファイルハンドルなどの資源を予測可能に解放できます。

### 詳細

- **非原子的カウントが既定**。タスク境界を越えた値(チャネル送信、`spawn` の捕捉、`Atom`、定数)は、その時点でオブジェクトグラフをたどって「共有済み」ビットを立て、以後は原子的操作になります。すでに共有済みの部分グラフは再走査しません。不変値は共有済み後も内容が変わらないため、これ以外の同期は不要です。
- **RC 省略**: 借用推論(引数として渡すだけで保持しない参照に `inc`/`dec` を挿入しない)と、`inc` の直後の `dec` の相殺。
- **再利用**: `dec` でちょうど 0 になった直後に同じサイズの割り当てがあれば、メモリを再利用します(`data` の `with` や `Array#push` が割り当てなしで済む)。
- **サイクル回収**: 不変値は作られた時点で自分より古い値しか指せないので、サイクルを作れません。サイクルを作りうるのは `var` フィールドを持つオブジェクトと、再代入される捕捉変数のボックスだけです。これらのオブジェクトだけを候補として、Bacon–Rajan の試行削除を低頻度で走らせます。ほとんどのプログラムでは候補集合が小さく、回収コストは無視できます。
- **`Int` の小さな値、`Float`(型が静的なとき)、`Bool`、`Nil`、`Symbol`** はカウント対象外です。
- **弱参照**は提供しません(必要になる状況が可変オブジェクトのサイクルに限られ、サイクル回収で解決するため)。

### 採用しなかった案

- **世代別トレース GC(Go/Erlang/Ruby)**: 割り当てが速く、カウント操作のオーバーヘッドがありませんが、上の 1〜3 を失います。不変値をその場で更新できないと、永続データ構造のコストを常に払うことになります。
- **原子的 RC を常時(Swift)**: 単純ですが、原子的操作のコストが全体にかかります。Lean 4 方式の「共有された部分グラフだけ原子的」は、タスク境界が明示的な Quarz に適合します。

## 6. ネイティブコード生成

- 小さな命令ビルダのトレイトに対して書かれた生成器が LLVM IR を書き出し、`clang -O2` でコンパイルします。バイナリは LLVM の最適化器と unwind 表を得ます(型付き入口は活性化レコードを積みません。バックトレースをネイティブスタックから復元するためです。§9 参照)。プロセス内で機械語を生成してビルドを速くする 2 つ目のバックエンド(Cranelift)もありましたが、削除しました。開発にはインタプリタがあり、残すと専用のレジスタ共有の方針、ランタイム呼び出しの二重の宣言、ビルドのテストの時間の約 3 分の 1 がかかっていたためです。
- `Int` のあふれ検査は `llvm.sadd.with.overflow`、`Float` は非ボックス、`data` の小さなインスタンスはスカラー置換により構造体として扱われます。
- 例外と非局所的な脱出(ブロックからの `break`/`return`、`exit`)は、コンパイル済みの各関数が返して呼び出し側が検査する状態コードです。unwind 表はバックトレースの復元にだけ使います。
- タスクのスタックはタスクごとに予約し、切り替えはスタックポインタの差し替えです(`corosensei`)。
- 出力はランタイム(`libquarz_vm.a`)を静的に、C ライブラリを動的にリンクします。共有ライブラリの生成(`--shared`)は*予定*です。

## 7. REPL と開発時の体験

- `quarz repl` は入力を型検査してから実行します。`class` や `def` を対話的に追加できます。既存の定義を変えたときに REPL が「その定義を使っているものごと」再コンパイルして差し替える機能(ホットリロード)は*予定*で、今は再定義がエラーになります(§9)。これは REPL だけの機能で、プログラムの意味論には影響しません。
- 型エラーは Ruby 風の位置表示に、期待型と実際の型を添えて出します。絞り込みのヒント(「ここで `x` は `String?` です。`if x` で絞り込めます」)は*予定*です。
- ファイル変更時に再実行する `quarz run --watch` は*予定*です。

## 8. 実装言語と構成

実装言語は **Rust** です。フロントエンド、VM、ランタイムをすべて Rust で書き、`cargo build` で単一バイナリ `quarz` を得ます。

### なぜ Rust か

Quarz の実装で最初から必要になるものを並べると、Rust のエコシステムで埋まる部分が多いことが決め手です。

| 必要なもの | Rust での手当て |
|---|---|
| スタックフルなタスクの切り替え | `corosensei` |
| ワークスティーリングスケジューラ、チャネル | `crossbeam` のデック・同期プリミティブ(予定。今のスケジューラは 1 スレッドで動き、どちらも使わない) |
| 非同期 IO | ソケットは、Linux では epoll を直接使い(各ソケットを edge-triggered で一度だけ登録)、それ以外では `polling`(kqueue)。ファイル全体の操作・ディレクトリとメタデータの操作・名前解決・`connect`・子プロセス、開いた `File` と標準入力のバッファの補充と書き出しは補助スレッド。標準出力と標準エラーへの書き込みは同期処理 |
| 多倍長整数、正規表現、Unicode | `num-bigint`(または `rug`)、`regex`、`unicode-*` |
| 永続ベクタ・HAMT | RC の一意性を使ってその場で更新するため自前。`im`/`rpds` を参考にする(予定。今のコレクションはコピーオンライトのベクタと `indexmap` の表) |
| AST・型の処理 | `enum` とパターンマッチ |
| ネイティブのバックエンド | LLVM。テキストの IR を `clang` でコンパイルする |

検討した他の候補:

- **C**: CRuby と同じ流儀で書けるが、上の表のライブラリ群を vendor する手間と、スケジューラ・チャネルという最もバグを出しやすい部分を安全装置なしで書くことになる点で見送り。
- **OCaml(フロントエンド)+ C(ランタイム)**: 型検査器を書くには最良だが、Quarz の本体はランタイム寄り(RC、スケジューラ、その場更新)で、そこと型検査器を別言語にするとインタプリタの起動パスが複雑になる。
- **Zig**: ランタイムには向くが、言語と標準ライブラリの安定性が不足。
- **Ruby で stage0 を書き、早期にセルフホスト**: Quarz への移植は楽だが、`quarz run` のたびに Ruby で型検査することになり、開発用インタプリタとしての起動の速さを失う。セルフホストは必須ではなく、やるとしても Rust 実装が安定した後とする。

### Rust で書く上での方針

- **`unsafe` はランタイムに閉じ込める。** タグ付きポインタ、RC の非原子/原子切り替え、その場更新は Rust の所有権モデルの外側にあり、ここは「Rust で書く C」になる。ランタイム(`quarz-vm`。コード生成器にも 1 か所ある)の内部だけに `unsafe` を置き、フロントエンドには安全な API だけを見せる。
- **AST と型は arena で持つ。** `Rc<RefCell<_>>` の木は作らず、`Vec` + `NodeId(u32)`/`TypeId(u32)` の index で参照する。借用検査との衝突を避け、QIR への変換やキャッシュの直列化も単純になる。
- **構文解析器は手書きの再帰下降。** Ruby 系の文法は字句解析器が状態を持つ(`{` のブロック/ハッシュ、`name: Type` のラベル、ヒアドキュメント、文脈キーワード)ので、Prism と同じく手書きが向く。
- **クレートを分けてコンパイル時間を局所化する。**

### クレート構成

```
quarz/
  Cargo.toml          ワークスペース
  crates/
    quarz-syntax      字句・構文解析、AST(位置情報付き)、エラー報告
    quarz-types       名前解決、型検査、Shareable 導出(.qzi は予定)
    quarz-ir          QIR(レジスタマシン IR)と実行時メタデータ(RtWorld)
    quarz-lower       型検査済み AST → QIR
    quarz-vm          ランタイム(オブジェクトモデル、RC、スケジューラ、チャネル、IO、ネイティブ)と QIR インタプリタ。
                      コンパイル済みプログラムがリンクする静的ライブラリでもある
    quarz-aot         QIR → 機械語(clang 経由の LLVM)とリンク
    quarz-cli         quarz run / check / ir / build / repl
  std/                標準ライブラリ(Quarz で書く部分)
  docs/
  examples/
```

### 実装の順序

1. `quarz-syntax`: 字句解析器、構文解析器、AST。`examples/` が構文解析を通ることを目標にする。
2. `quarz-types`: 名前解決と型検査。まず単相のクラス・メソッド・合併型・フロー型付け、次にジェネリクス、`data`/`enum`、パターンの網羅性、`extension`。
3. ランタイムの最小部分: オブジェクトモデルと RC、`Int`/`String`/`Array`/`Hash`。
4. `quarz-vm`: QIR とレジスタ VM。`quarz run` で `examples/hello.qz` と `shapes.qz` を動かす。
5. ランタイムの並行部分: タスク、スケジューラ、チャネル、`Atom`、非同期 IO。`wordcount.qz`、`pipeline.qz`、`bank_actor.qz` を動かす。
6. 標準ライブラリの拡充、REPL、`.qzi` による分割コンパイルとキャッシュ。
7. ネイティブバックエンド(LLVM)。
8. パッケージ管理、`fmt`、LSP。

## 9. 現在の実装(v0.0.1)

現時点の実装は、上の計画と意図的にいくつかの点で異なります。計画は引き続き設計の向かう先を示しています。

- **プログラムは QIR に変換され、レジスタ VM が解釈します**。型検査器が木に型、解決済みの呼び出し先、変数スロットを付け、`quarz-lower` がメソッド・ブロック・定数初期化子・ファイルのトップレベルをそれぞれ QIR の関数にし(`quarz ir FILE` で表示できます)、`quarz-vm` がそれを実行します。ブロックに捕捉されるローカル変数はヒープ上のフレームに、それ以外はレジスタに置きます。キーワード引数はランタイムが束縛し、デフォルト値は呼ばれた側のプロローグで評価します。ブロックからの `break`/`return` はランタイムを通るステータスコードで、`ensure` はあらゆるフローを受けて再開するハンドラブロックです。`ensure` 領域を抜ける通常の `return`/`break` は本体をインライン展開して実行します。`Int`/`Float` の演算子と自動生成のフィールドアクセサはメソッドディスパッチを迂回します。各命令はソース行を持つので、例外は(タスクごとに)`file:line:in name` 形式のバックトレースを持ち、`__LINE__` も解釈実行・コンパイル済みの両方で動きます。
- **値は `Rc` ベースです**。不変コレクションは `Rc` で共有するベクタと挿入順を保つ表で、更新は `Rc::make_mut` により参照が一意でなければコピーします。`Int` だけ・`Float` だけの配列は機械語の語を、キーと値がすべて `Int` のハッシュは `Int` から `Int` への表を持ちます。インタプリタでもコンパイル済みコードでも同じです。15 バイト以下の文字列は値そのものの中に置かれます(割り当ても参照カウントもなく、コピーは 3 語のコピーです)。それより長い文字列は共有の `Rc<str>` です。どちらかで観察できる違いはありません(`==`、`equal?`、ハッシュ、順序はテキストを比較します)。最後に読まれる値は複製せずにムーブします。`xs = xs.push(x)` のレシーバも、呼び出し側がもう読まない引数もそうで、引数は呼び出し先の仮引数が引き継ぎます。そのため `def add(xs, v) = xs.push(v)` に対する `ys = add(ys, x)` もその場で更新されます。`QUARZ_COUNT_COPIES=1` を付けると、共有されたコレクションを更新のために複製した回数を終了時に報告します(インタプリタでもコンパイル済みのコードでも同じです)。その場で更新されるはずのループが一度も複製しないことを、テストで確かめています。§5 の Perceus 流の一般的な再利用は今後の課題です。`Rc` はランタイム自前の型です(`quarz-vm` の `rc.rs`)。別のタスクに渡る値には「共有」の印が付き、共有された値の参照カウントだけを原子的に更新します([04-concurrency.ja.md](04-concurrency.ja.md) §7)。タスク内の割り当て領域は 1 語目に参照カウントを持ちます。共有された領域は 1 語目が 0 で、参照カウントは 2 語目にあります。そのためコンパイル済みコードは 1 語だけを読み、0 でないカウントを増やす処理と 1 より大きいカウントを減らす処理をインラインで行い、それ以外はランタイムを呼びます。コンパイル済みの `dispatch` と `objects`(10 倍に延ばしたもの)では、この確認で命令数が 7〜10% 増えますが、サイクル数の差は測れない程度です。
- **タスクはスタックフルなコルーチン(`corosensei`)で、ワーカースレッドが動かします(M:N)。ワーカーの数は `QUARZ_THREADS` で、今のところ既定は 1 です**。スケジューリングは協調的で、チャネル操作、`sleep`、`await`、`Task.yield`、`loop` の中、I/O の待ちで切り替わります。ソケットはスケジューラの epoll/kqueue のリアクタで待ち、ファイル全体の操作、ディレクトリとメタデータの操作、名前解決、子プロセス、開いた `File` と標準入力の読み書きのうちバッファで済まないものは補助スレッドで実行して、呼んだタスクだけが待ちます。`Task.blocking { }` はブロックを別スレッドの 2 つ目のインタプリタで実行し、不変な値だけが行き来します。標準出力と標準エラーへの書き込みは同期的です。各タスクは仮想メモリ 16 MiB(メインタスクは 256 MiB)のスタックを予約し、超えると `SystemStackError` になります。デッドロック(全タスクが待機し、タイマーも保留中の I/O もない)は `DeadlockError` でプログラムを停止します。
- **ワーカースレッド。** 各ワーカーは自分のインタプリタを持ち、共有の `Program` と `Global` の上で動きます。`Program` は読み込んだプログラムから作るもので、`Send + Sync` です(コンパイル時に検査します)。`Global` は実行中のプログラムが積み上げる状態です。シンボル表(読み書きロックの中にあり、各インタプリタは引いた名前の写しを手元に持ちます)、定数(値が決まった後はロックなしで読めるセルで、初期化子は一度だけ実行され、その間ほかのタスクは待ちます)、フィールドのない enum の値、`at_exit` のブロック、標準出力がここにあります。ワーカーのインタプリタは、そのワーカーに初めてタスクが置かれたときに、そのスレッドの上でプログラムの写しから作ります。ワーカーはそれぞれ実行キュー、タイマー、epoll の reactor、タグの範囲を持ちます。新しいタスクは各ワーカーに順に置かれ、そこにとどまります(コルーチンとその下のネイティブのフレームはスレッドに結びついています)。work stealing はまだありません。タスクはほかから「ワーカーとその中の番号」で指されます。別のワーカーのタスクを起こすときは、そのワーカーの受信箱に入れて reactor を起こします。あるタスクから別のタスクに渡る値(チャネルで送る、`spawn` で捕捉する、`Atom` に入れる、タスクが返す)は、参照先も含めて「共有」の印が付き、共有された値の参照カウントだけを原子的に更新します(`rc.rs`。共有された割り当て領域は 1 語目が 0 で、カウントは 2 語目にあるので、コンパイル済みコードは 1 語だけを読みます)。定数、トップレベルの `self`、enum の値は不死で、参照カウントを更新しないので、それらを使うワーカーどうしがキャッシュラインを奪い合いません。タスクが共有するものは、状態をロックの中に持ちます。チャネルはスピンロック(ワーカーが 1 つの間は、取得も普通の書き込みです)、タスクのハンドルは原子変数とロック、`Atom` の値と IO ハンドルの状態は mutex の中です。ソケットは、そのソケットを待つタスクがいるワーカーごとに、そのワーカーの poller に登録します。デッドロックは、どのワーカーにも実行できるタスク、タイマー、IO がなく、どのワーカーへ向かっているものもない状態です。メインのワーカーが、自分のタスクを挙げて報告します。プログラムはメインのタスクで(またはどれかのタスクの `exit` で)終わり、ほかのワーカーは止まります(そのタスクは巻き戻しません)。REPL と `Task.blocking` のヘルパースレッドは、ワーカー 1 つで動きます。`fib(27)` を計算する 8 つのタスクは、ワーカー 1 つで 0.33 秒、4 つで 0.12 秒です。echo のベンチマークでは、ワーカー 4 つで 16 接続のとき Go の 4 スレッドと同じ往復数を、64 と 256 接続では約 90% を処理します(bench/net/README.md)。ワーカーが 1 つのとき、2 つのタスクの間の 20 万回の往復は、ワーカーを入れる前より命令数が 3% 多くなります。
- **REPL**(`quarz repl`)は宣言・変数・実行中のタスクを入力をまたいで保持し、各入力を累積したプログラムに対して増分で検査します。クラスやメソッドの再定義はエラーです(新しい名前を使ってください)。§7 のホットリロードは未実装です。`require` と `require_relative` は REPL でも使え、読み込んだファイルのトップレベルを一度だけ実行します。
- **`Bytes`・`Time`・`json` ライブラリ**。`Bytes` は不変のバイト列で、`b"..."` リテラル、`Bytes::Builder`、`String#to_bytes`/`encode`、`Bytes#decode`(UTF-8、ASCII、ISO-8859-1)を持ちます。`Time` は UTC オフセット付きの時刻(`Time.now`/`utc`/`local`/`at`/`parse`/`iso8601`、`strftime`、`Duration` との加減算)で、`Time.monotonic` は単調増加クロックを `Duration` で返します。`require "time"` は受け付けますが不要です。`require "json"` で `JSON.parse -> JSON::Value` が使えます。`JSON::Value` は `Null`・`Boolean`・`Integer`・`Number`・`Text`・`List`・`Map` の 7 つのバリアントを持つ enum で(それぞれ値を持ち、`as_s`・`as_i?`・`[]` などのアクセサがあります)、`JSON.generate`/`pretty_generate` と `to_json` も提供します。クラスは `to_json -> String` を定義すれば JSON 表現を変えられます。パーサと生成器はネイティブで、残りは Quarz で書かれています(`std/json.qz`)。
- **`quarz build` はネイティブ実行ファイルを生成します**。`quarz-aot` が QIR の各関数を機械語にします。既定では LLVM で(モジュールを LLVM IR として書き出し `clang -O2` でコンパイルします。`QUARZ_CLANG` でコンパイラを指定でき、`QUARZ_KEEP_IR` で出力の隣に `.ll` `return z if y >= x` のように、非ボックス化した値の算術・比較・コピー・分岐だけで宣言どおりの型の `return` に至る部分があるとき)、その部分を別の入口関数としてもう一度コンパイルし、呼び出し側はそれを呼び、LLVM - **実装中に決めた細かい事項**(他の章を設計のまま保つためにここにまとめます): `*rest` の後ろの引数はキーワード専用(`*` 単独の後ろと同様)。`[]?` はメソッド名(`xs[i]?`)。`x in pattern` は引数リストの中でも書ける。配列リテラル同士の `[a, b] <=> [c, d]` はタプルとして要素ごとに検査する。複数の引数を宣言したブロックが 1 つの配列またはタプルを受け取ると Ruby と同様に展開する。`Object` は `Kernel` を `include` し、`puts` は全オブジェクトのプライベートメソッド。`IO` ハンドルは `Shareable`(ランタイムがアクセスを直列化する)。prelude は組み込みを `native def` で宣言する。`Comparable#clamp` はネイティブで `self` を返す。`case/in` の異なるアームで束縛されるパターン変数は別の変数。合併型・`data`・`enum`・`Nil`・`Bool` の選択肢を取りこぼす `case/in` はエラー、`Int` のような開いた型の値の取りこぼしは警告(実行時は `NoMatchingPatternError`)。型テストで主題を覆う `case/when` に `else` は不要。`break` のない `loop` の型は `Nothing`。浮動小数点数は Ruby と同じ形式で表示する。`Hash` のキーと `Set` の要素は、不変の組み込み値と `data`/`enum` の値については構造的等価、クラスのインスタンスについては同一性で比較する(キーの比較にユーザー定義の `==`/`hash` は使われない)。サブクラスや enum のバリアントがオーバーロードされたメソッドの一方だけをオーバーライドした場合、他方に解決された呼び出しはスーパークラス側に届く(ランタイムは名前だけでなくシグネチャでディスパッチする)。
