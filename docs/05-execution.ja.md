# 実行モデル: インタプリタと AOT コンパイラ

Quarz は 1 つのフロントエンドと 1 つのランタイムを、2 つのバックエンド(QIR のインタプリタと機械語)で共有します。開発中は `quarz run` で起動の速さと REPL を、本番は `quarz build` で実行速度を取り、**両者の観測可能な挙動は同一**です。

```
                    ┌────────────┐   ┌──────────────┐   ┌───────────────┐
  foo.qz ─────────▶ │ 字句・構文 │─▶ │ 名前解決・型 │─▶ │  QIR(型付き  │
  (+ require 先)    │   解析     │   │   検査       │   │   中間表現)   │
                    └────────────┘   └──────────────┘   └───────┬───────┘
                                                                 │
                       ┌─────────────────────────────────────────┼─────────────────────┐
                       │ quarz run / repl                        │ quarz build          │
                       ▼                                         ▼                      │
               ┌───────────────┐                     ┌────────────────────┐             │
               │ QIR の        │                     │ 最適化(脱仮想化、 │             │
               │ インタプリタ  │                     │ インライン化、RC   │             │
               │               │                     │ 省略、非ボックス化)│             │
               └───────┬───────┘                     └─────────┬──────────┘             │
                       │                                       ▼                        │
                       │                             ┌────────────────────┐             │
                       │                             │ LLVM IR → 機械語   │             │
                       │                             │ (clang)            │             │
                       │                             └─────────┬──────────┘             │
                       ▼                                       ▼                        │
               ┌──────────────────────────────────────────────────────────┐             │
               │  libquarz ランタイム(参照カウント、スケジューラ、コピー │ ◀───────────┘
               │  オンライトのコレクション、文字列、多倍長整数、IO、      │
               │  チャネル、正規表現)                                    │
               └──────────────────────────────────────────────────────────┘
```

## 1. コマンド

| コマンド | 動作 |
|---|---|
| `quarz run app.qz [args]` | 型検査し(変わっていないファイルの検査結果は再利用する。§2)、QIR に変換(lowering)して解釈実行する |
| `quarz repl` | REPL。入力ごとに型検査し、定義を追加できる(再定義は不可、代わりに新しい名前を使う) |
| `quarz check app.qz` | 型検査のみ |
| `quarz build app.qz -o app` | ネイティブ実行ファイルを生成(LLVM で最適化) |
| `quarz ir app.qz` | 全関数の QIR を表示する(変換結果のデバッグ用)。`quarz tokens` と `quarz parse` はトークンと構文木を表示する |
| `quarz test` | `test/**/*_test.qz`、または指定したテストファイルを実行。コンパイラが見つける Test::Unit 風のクラス([12-testing.ja.md](12-testing.ja.md))。`--release` でコンパイルして実行 |
| `quarz doc [NAME]` | 宣言のドキュメントを表示するか、cog のサイトを生成する(`--html`)。宣言の上のコメントから([13-doc-comments.ja.md](13-doc-comments.ja.md))。その中の例は `quarz test` が実行する |
| `quarz fmt` | 整形(*予定*) |
| `quarz cog add <git-url>` | パッケージ管理。cog は `Cog.lock` でコミットに固定された git リポジトリ。マニフェストは `Cog.toml`([10-cogs.ja.md](10-cogs.ja.md))。`run`、`check`、`build`、`ir` はスクリプトのほか、アプリケーション(`Cog.toml` のあるディレクトリ、その `src/main.qz`、または省略して現在のディレクトリを囲むもの)を受け付ける |

## 2. コンパイル単位と分割コンパイル

1 ファイルが 1 コンパイル単位です。単位ごとに分けて行い、実行をまたいで保持するのは検査です。その後(QIR の最適化とコード生成)は常にプログラム全体を見ます。ファイルの検査が後のファイルに左右されないのは、言語の規則によります。トップレベルの `extension` は宣言した cog やプログラムの中だけで有効で(01-syntax.ja.md §7)、`==` はサブクラスを持てない型だけを絞り込み(02-types.ja.md §6)、`nil?` と `is_a?` は再定義できず(01-syntax.ja.md §3)、`data` 型の配置はそれを定義した場所で決まり、戻り値型は推論せずに宣言します(02-types.ja.md §5)。この独立性に、2 つのことが乗っています。プレリュードと標準ライブラリは `quarz` のビルド時に、プログラムがまだ存在しないうちに検査されます。この規則がなければ、プログラムの extension、独自の `==` を持つサブクラス、`nil?` の再定義が、それらの本体の検査結果を変えてしまいます。また、保持したファイルの検査の鍵は、ほかのファイルの本体を除いた宣言です。それができるのは、呼び出しがメソッドについて必要とすること(戻り値型と、ブロックを保持するか)がすべてシグネチャにあるからです。(組み込みの値クラスを継承できないのは別の話です。その値はランタイム固有の表現なので、サブクラスのオブジェクトをその値として扱えません。)単位の QIR も後の単位に左右されません。クラス階層解析による書き換え(どこでも上書きされないフィールドのリーダーをフィールドの読み出しに、サブクラスのないクラスのクラスメソッドでの `new` を通常の生成に)はプログラムをリンクしてから行い、フィールドの既定値はそれを宣言したクラスで一度だけ QIR に変換します。

**プレリュードと標準ライブラリ。** `quarz` をビルドするときに宣言・検査し、コマンドはその状態(実行ファイルに埋め込んだ `quarz_types::PreludeState`。`quarz-cli/build.rs` が作ります。`QUARZ_NO_PRELUDE_CACHE=1`(`0` ではなく)でソースから検査します)から始めます。プレリュードの状態は 1 つです。標準ライブラリのモジュールは、プログラムが読み込む組(`json`、`time`、`socket`、`json`+`socket`+`http`、`test`)ごとに検査し、各組がそのモジュールをプログラムの最初の単位として持つ状態になります。単位番号は固定で(`load::std_unit`)、どのプログラムでも同じ番号です。別の組み合わせを読み込むプログラムは、モジュールをソースから検査します。標準ライブラリが公開する名前は、構文解析せずに宣言の行から読みます。そのメソッドはプレリュードのものと同じく、呼ばれうるものだけを QIR に変換します(§9)。`puts 1` は 1 億 2160 万命令かかっていたのが 2320 万命令です。

**ファイルの検査結果の保持(`quarz_types::cache`)。** 検査は 1 つの世界に追加していきます。クラス、メソッド、定数、型の別名、extension、型パラメータは宣言された順に番号が付き、検査結果は構文ノードをキーにした表で、ノードは単位の範囲(`load::unit_base`)の中で番号が付いています。ファイルの本体の検査が記録したもの(ノードの検査結果、メソッドのフレームの大きさ、定数の型、`Self` の生成箇所、警告)を、キーをつけて保存します。キーは、コンパイラのビルド、そのファイルの構文木、全ファイルの*インターフェース*(`cache::interface`。各実体の、本体・既定値や定数の値・位置を除いた宣言)、そしてムーブメントならその cog(名前、ルートモジュール、依存のキー)とそのファイルの属する cog です。次の実行では、ファイルの構文解析と宣言はやり直し(軽いので)、キーが変わっていなければ本体は検査しません。保存した結果を読み戻し、番号を付け替えます(`reloc`)。その中の番号のうち実体を指すものは、それが誰のものかを表します。プレリュードと標準ライブラリのものはその番号のままです。別のファイルのものは、そのファイル(パス)と、そのファイルが持つ実体の中での位置で書き、読み戻すときにこのプログラムでの位置を引きます。ノード番号と位置はそのままです。キーの構文木に含まれているので、読み戻すファイルは同じ範囲にあり、それより前に読み込むファイルを追加・削除・並べ替えると検査し直します。そのため、本体の変更ではそのファイルだけを検査し直し、シグネチャ・定数の初期化式・型の別名の変更では全ファイルを検査し直します。定数の型は初期化式から推論するのでインターフェースには含めず、検査のあとで比べて、食い違っていればキャッシュを使わずにプログラムを検査し直します。診断はファイル順・位置順に出るので、検査したときと読み戻したときで同じ順番です。

キャッシュは既定で有効で、ユーザーが実行するすべてのプログラムで共有します。Go のビルドキャッシュや Crystal のものと同じ形です(`quarz run file.qz` はスクリプトをその場で実行するので、Cargo の `target/` のように置いておくプロジェクトのディレクトリがありません)。場所は `$XDG_CACHE_HOME/quarz`(`~/.cache/quarz`)です。`QUARZ_CACHE_DIR` で場所を変えられ(テストスイートのものは `.cargo/config.toml` により `target/` の下)、`QUARZ_NO_CACHE=1` で無効にできます。エントリは別名で書いてから改名し、チェックサムを持ち(壊れていればミス扱い)、30 日使われなかったものは消します(エントリを書くときに、1 日に 1 回まで探します)。数百行の fixture では、検査結果を再利用すると `quarz check` が 2600 万命令から 1890 万命令になります(最初に書き出すときは 200 万命令多くかかります)。

**全体のまま行うもの。** 単位ごとに分けるのは検査までで、コンパイルは分けません。QIR の最適化とコード生成は常にプログラム全体を見ます。Rust の crate が MIR を持ち、使う側で実体化やインライン化をするのと同じ形です。これがあるから、`virtual`(や Swift・Kotlin の `open`)がなく、どのメソッドも上書きできるままで、直接呼び出しにコンパイルできます。単位を単独で機械語にすると、そのメソッドのどれを後の単位が上書きするか分からないため、自分の public メソッドの呼び出しはすべてディスパッチのまま残り、インライン化もできず、shake(§9)はそのメソッドを1つも消せません。クラスが実行時に作られないため、クラス階層解析は完全です。全体を見る解析は、CHA、脱仮想化、インライン化、shake、`quarz_ir::field_slots` のフィールド配置、今後の単相化です。

**検討して作らなかったもの。** 単位ごとのインターフェースファイル(`.qzi`)。宣言と QIR を持ち、ファイルの構文解析と宣言の代わりに読み、標準ライブラリはそれを配布する、というものです。ファイルの構文解析と宣言は数百万命令で、QIR への変換のうちファイルごとにできるのは翻訳の部分だけ(最大の fixture で 5800 万命令のうち 1000 万。その後のパスは全体を見ます)なので、どちらも QIR の番号の付け替えを作る手間に見合いません。標準ライブラリは検査した状態をコマンドに埋め込んでいます。`quarz run` 用に、ライブラリの Quarz のメソッドも機械語で持つかどうか(単独でコンパイルするので上のディスパッチは残りますが、インタプリタなら許容できます)は未定です。

## 3. QIR

QIR(Quarz Intermediate Representation)は、両方のバックエンドが入力にする中間表現です。レジスタマシン(レジスタは再代入できる)で、基本ブロックからなり、各ブロックにハンドラのブロックを付けられます。Ruby 風の構文は QIR に落ちる段階で単純化されます。

- メソッド呼び出しは、チェッカーが解決できるところでは解決済みです(呼び出しはメソッドを指し、サブクラスが上書きしていればレシーバのクラスで振り分けます)。解決できなければ実行時に名前で探します。コンストラクタ、手続きの呼び出し、`yield`、`super` には専用の呼び出し種別があります。
- よく使うイテレータ(`Int`・`Array`・リテラルの範囲に対する `times`、`upto`、`each`、`map`、`select` など)のブロックはその場のループに変換し、`break`/`next` はジャンプになります。それ以外のブロックはクロージャで、そこから抜ける `break`/`return` はランタイムを通る状態コードです。小さなメソッドはインライン化します。
- 値はタグ付きです(合併型に別の表現は要りません)。`Int` の演算はあふれを検査し、あふれたら `OverflowError` を投げます(任意の大きさは `Integer` が持ちます)。
- 参照カウントとタスクの切り替えは、ランタイムとバックエンドが生成するコードが行い、QIR の命令にはなりません。ただし、値を複製せずにムーブする箇所は QIR に書かれます。レジスタの最後の読み出しになるコピーや呼び出しの引数は値をムーブするので(`Take`、呼び出しのムーブされる被演算子)、渡したコレクションも参照は一意のままです。解放が観測できる変数(03-data-model §4)は、スコープの終わりの `Release` が最後に読みます。`Release` はそこで変数を解放し、解放されたものの `deinitialize` を実行します。その後のパスは、変数の最後の使用(値がムーブされる呼び出し)からスコープの終わりまでの間に区別できるものが何もない `Release` を取り除きます。間にある数値演算や他のレジスタのコピーは区別に関わりません(Swift の deinit barrier)。そのため、値はこれまでどおりその呼び出しにムーブされます。
- 最適化のあと、値が同時に生きることのないレジスタは同じ番号を共有します(参照カウントされる値を持ちうるレジスタとそうでないものは分けます)。インライン化した呼び出し先を含むメソッドでも、レジスタは百ではなく十数で済みます。

インタプリタとコンパイラの意味論が一致する根拠は、どちらも同じ QIR を入力にし、同じランタイム関数を呼ぶことです。QIR から先で許される差は性能だけで、CI では同じテストスイートを両モードで実行して差分検査(differential testing)を行います。

## 4. インタプリタ

- **インタプリタは QIR の命令をそのまま実行します**。別のバイトコードはありません。レジスタはタグ付きの値を持ちます。`Int`・`Float`・`Bool` は割り当てられませんが、タグは付いています。頻出の操作(`Int`/`Float` の算術と比較、配列の要素の読み出しと追加、長さ、フィールドの読み書き)には専用の命令があります。
- 型情報があるため、動的言語のインタプリタに必要なインラインキャッシュやガードがありません。目標は Lua/LuaJIT インタプリタ級の速度で、Ruby(YJIT なし)の 3〜10 倍程度を想定しています。
- 将来、ベースライン JIT(QIR → 機械語をその場で生成)を追加できますが、「本番は AOT」を前提にしているため優先度は低く置いています。

## 5. メモリ管理

**参照カウント(RC)+ 一意性によるその場更新 + 可変オブジェクト限定のサイクル回収**を採用します。

今は値を原子的操作なしで参照カウントし、更新は参照が一意でなければコピーします(§9)。以下に書く、共有ビットによる原子的カウント、一般的な再利用、サイクル回収はまだ作っていません。別のスレッドへ値を渡すのはコピーによるだけで(`Task.blocking`)、可変オブジェクトのサイクルは回収されません。

### なぜ参照カウントか

1. **不変値のその場更新**: 参照カウントが 1 の不変値は、「新しい値を返す」操作をその場で破壊的に行えます(Lean 4 / Koka の Perceus)。Quarz の「不変を既定にしつつ速い」はこれに依存しています。
2. **AOT との相性**: トレース GC はネイティブコードのスタックマップ(LLVM statepoint など)か保守的スキャンが必要で、実装の難所です。RC はどちらも不要で、C FFI との境界も単純です。
3. **決定的な解放**: `ensure` と組み合わせて、ファイルハンドルなどの資源を予測可能に解放できます。

### 詳細

- **非原子的カウントが既定**。タスク境界を越えた値(チャネル送信、`Task.spawn` の捕捉、`Atom`、定数)は、その時点でオブジェクトグラフをたどって「共有済み」ビットを立て、以後は原子的操作になります。すでに共有済みの部分グラフは再走査しません。不変値は共有済み後も内容が変わらないため、これ以外の同期は不要です。
- **RC 省略**: 借用推論(引数として渡すだけで保持しない参照に `inc`/`dec` を挿入しない)と、`inc` の直後の `dec` の相殺。
- **再利用**: `dec` でちょうど 0 になった直後に同じサイズの割り当てがあれば、メモリを再利用します(`data` の `with` や `Array#push` が割り当てなしで済む)。
- **サイクル回収**: 不変値は作られた時点で自分より古い値しか指せないので、サイクルを作れません。サイクルを作りうるのは `var` フィールドを持つオブジェクトと、再代入される捕捉変数のボックスだけです。これらのオブジェクトだけを候補として、Bacon–Rajan の試行削除を低頻度で走らせます。ほとんどのプログラムでは候補集合が小さく、回収コストは無視できます。
- **`Int` の小さな値、`Float`(型が静的なとき)、`Bool`、`Nil`、`Symbol`** はカウント対象外です。
- **決定的な解放とその範囲**: 値は最後の参照がなくなったときに解放されるので、ファイルハンドルが閉じる時点や `deinitialize`(03-data-model §4)が実行される時点は決まっています。最後の使用で解放すると、その時点がソースから読み取れるより早くなります(ポート番号を知るためだけに使ったサーバーソケットがすぐ閉じます)。そこで、解放が観測できる変数はスコープの終わりまで生き、それ以外の変数はこれまでどおり最後の使用でムーブされます。
- **弱参照**は提供しません(必要になる状況が可変オブジェクトのサイクルに限られ、サイクル回収で解決するため)。

### 採用しなかった案

- **世代別トレース GC(Go/Erlang/Ruby)**: 割り当てが速く、カウント操作のオーバーヘッドがありませんが、上の 1〜3 を失います。不変値をその場で更新できないと、永続データ構造のコストを常に払うことになります。
- **原子的 RC を常時(Swift)**: 単純ですが、原子的操作のコストが全体にかかります。Lean 4 方式の「共有された部分グラフだけ原子的」は、タスク境界が明示的な Quarz に適合します。

## 6. ネイティブコード生成

- 小さな命令ビルダのトレイトに対して書かれた生成器が LLVM IR を書き出し、`clang -O2` でコンパイルします。バイナリは LLVM の最適化器と unwind 表を得ます(型付き入口は活性化レコードを積みません。バックトレースをネイティブスタックから復元するためです。§9 参照)。プロセス内で機械語を生成してビルドを速くする 2 つ目のバックエンド(Cranelift)もありましたが、削除しました。開発にはインタプリタがあり、残すと専用のレジスタ共有の方針、ランタイム呼び出しの二重の宣言、ビルドのテストの時間の約 3 分の 1 がかかっていたためです。
- `Int` のあふれ検査は `llvm.sadd.with.overflow`、`Float` は非ボックス、`data` の小さなインスタンスはスカラー置換により構造体として扱われます。
- 例外(`SystemExit` を投げる `exit` も含む)と非局所的な脱出(ブロックからの `break`/`return`、デッドロックなどによるプログラムの終了)は、コンパイル済みの各関数が返して呼び出し側が検査する状態コードです。unwind 表はバックトレースの復元にだけ使います。
- タスクのスタックはタスクごとに予約し、切り替えはスタックポインタの差し替えです(`corosensei`)。
- 出力はランタイム(`libquarz_vm.a`)を静的に、C ライブラリを動的にリンクします。共有ライブラリの生成(`--shared`)は*予定*です。

## 7. REPL と開発時の体験

- `quarz repl` は入力を型検査してから実行します。`class` や `def` を対話的に追加できます。既存の定義を変えたときに REPL が「その定義を使っているものごと」再コンパイルして差し替える機能(ホットリロード)は*予定*で、今は再定義がエラーになります(§9)。これは REPL だけの機能で、プログラムの意味論には影響しません。
- 型エラーは Ruby 風の位置表示に、期待型と実際の型を添えて出します。絞り込みのヒント(「ここで `x` は `String?` です。`if x` で絞り込めます」)は*予定*です。
- ファイル変更時に再実行する `quarz run --watch` は*予定*です。

## 8. 実装言語と構成

実装言語は **Rust** です。フロントエンド、VM、ランタイムをすべて Rust で書き、`cargo build` で単一バイナリ `quarz` を得ます。

### なぜ Rust か

Quarz の実装で最初から必要になるものを並べると、Rust のエコシステムで埋まる部分が多いことが決め手です。

| 必要なもの | Rust での手当て |
|---|---|
| スタックフルなタスクの切り替え | `corosensei` |
| ワークスティーリングスケジューラ、チャネル | `crossbeam` のデック・同期プリミティブ(予定。今のスケジューラは 1 スレッドで動き、どちらも使わない) |
| 非同期 IO | ソケットは、Linux では epoll を直接使い(各ソケットを edge-triggered で一度だけ登録)、それ以外では `polling`(kqueue)。ファイル全体の操作・ディレクトリとメタデータの操作・名前解決・`connect`・子プロセス、開いた `File` と標準入力のバッファの補充と書き出しは補助スレッド。標準出力と標準エラーへの書き込みは同期処理 |
| 多倍長整数、正規表現、Unicode | `num-bigint`(または `rug`)、`regex`、`unicode-*` |
| 永続ベクタ・HAMT | RC の一意性を使ってその場で更新するため自前。`im`/`rpds` を参考にする(予定。今のコレクションはコピーオンライトのベクタと `indexmap` の表) |
| AST・型の処理 | `enum` とパターンマッチ |
| ネイティブのバックエンド | LLVM。テキストの IR を `clang` でコンパイルする |

検討した他の候補:

- **C**: CRuby と同じ流儀で書けるが、上の表のライブラリ群を vendor する手間と、スケジューラ・チャネルという最もバグを出しやすい部分を安全装置なしで書くことになる点で見送り。
- **OCaml(フロントエンド)+ C(ランタイム)**: 型検査器を書くには最良だが、Quarz の本体はランタイム寄り(RC、スケジューラ、その場更新)で、そこと型検査器を別言語にするとインタプリタの起動パスが複雑になる。
- **Zig**: ランタイムには向くが、言語と標準ライブラリの安定性が不足。
- **Ruby で stage0 を書き、早期にセルフホスト**: Quarz への移植は楽だが、`quarz run` のたびに Ruby で型検査することになり、開発用インタプリタとしての起動の速さを失う。セルフホストは必須ではなく、やるとしても Rust 実装が安定した後とする。

### Rust で書く上での方針

- **`unsafe` はランタイムに閉じ込める。** タグ付きポインタ、RC の非原子/原子切り替え、その場更新は Rust の所有権モデルの外側にあり、ここは「Rust で書く C」になる。ランタイム(`quarz-vm`。コード生成器にも 1 か所ある)の内部だけに `unsafe` を置き、フロントエンドには安全な API だけを見せる。
- **AST と型は arena で持つ。** `Rc<RefCell<_>>` の木は作らず、`Vec` + `NodeId(u32)`/`TypeId(u32)` の index で参照する。借用検査との衝突を避け、QIR への変換やキャッシュの直列化も単純になる。
- **構文解析器は手書きの再帰下降。** Ruby 系の文法は字句解析器が状態を持つ(`{` のブロック/ハッシュ、`name: Type` のラベル、ヒアドキュメント、文脈キーワード)ので、Prism と同じく手書きが向く。
- **クレートを分けてコンパイル時間を局所化する。**

### クレート構成

```
quarz/
  Cargo.toml          ワークスペース
  crates/
    quarz-syntax      字句・構文解析、AST(位置情報付き)、エラー報告
    quarz-types       名前解決、型検査、Shareable 導出、検査キャッシュ(§2)
    quarz-ir          QIR(レジスタマシン IR)と実行時メタデータ(RtWorld)
    quarz-lower       型検査済み AST → QIR
    quarz-vm          ランタイム(オブジェクトモデル、RC、スケジューラ、チャネル、IO、ネイティブ)と QIR インタプリタ。
                      コンパイル済みプログラムがリンクする静的ライブラリでもある
    quarz-aot         QIR → 機械語(clang 経由の LLVM)とリンク
    quarz-cli         quarz run / check / ir / build / repl
  std/                標準ライブラリ(Quarz で書く部分)
  docs/
  examples/
```

### 実装の順序

1. `quarz-syntax`: 字句解析器、構文解析器、AST。`examples/` が構文解析を通ることを目標にする。
2. `quarz-types`: 名前解決と型検査。まず単相のクラス・メソッド・合併型・フロー型付け、次にジェネリクス、`data`/`enum`、パターンの網羅性、`extension`。
3. ランタイムの最小部分: オブジェクトモデルと RC、`Int`/`String`/`Array`/`Hash`。
4. `quarz-vm`: QIR とレジスタ VM。`quarz run` で `examples/hello.qz` と `shapes.qz` を動かす。
5. ランタイムの並行部分: タスク、スケジューラ、チャネル、`Atom`、非同期 IO。`wordcount.qz`、`pipeline.qz`、`bank_actor.qz` を動かす。
6. 標準ライブラリの拡充、REPL、検査の分割とそのキャッシュ(§2)。
7. ネイティブバックエンド(LLVM)。
8. cog([10-cogs.ja.md](10-cogs.ja.md))、`fmt`、LSP。

- **プログラムは QIR に変換され、レジスタ VM が解釈します**。型検査器が木に型、解決済みの呼び出し先、変数スロットを付け、`quarz-lower` がメソッド・ブロック・定数初期化子・ファイルのトップレベルをそれぞれ QIR の関数にし(`quarz ir FILE` で表示できます。プレリュードのメソッドは、変換済みのものから呼ばれうるようになって初めて変換します。到達性は後述の `quarz_ir::shake` と同じく名前で判定し、REPL では入力ごとに新たに到達したものを変換します。ほとんどのプログラムでは約 200 の関数のうち数十個で済み、`quarz run` の起動が 4 分の 1 短くなります)、`quarz-vm` がそれを実行します。ブロックに捕捉されるローカル変数はヒープ上のフレームに、それ以外はレジスタに置きます。キーワード引数はランタイムが束縛し、デフォルト値は呼ばれた側のプロローグで評価します。ブロックからの `break`/`return` はランタイムを通るステータスコードで、`ensure` はあらゆるフローを受けて再開するハンドラブロックです。`ensure` 領域を抜ける通常の `return`/`break` は本体をインライン展開して実行します。`Int`/`Float` の演算子と自動生成のフィールドアクセサはメソッドディスパッチを迂回します。`x.nil?` も、レシーバの静的な型が許すクラス(とそのサブクラス。クラス階層解析で判定し、組み込みの値クラスにはありません)のどれも `nil?` を独自に定義していなければ値の検査(`IsNil`)になり、コンパイル済みコードは呼び出しなしに答えます(`Int?` を回すループが、そのためにランタイムを通ることはなくなります)。インタプリタはそうした演算子の結果とフィールドの値を、書き込み先のレジスタへ直接書きます。別の場所で作った値は、それを作った狭い書き込みの直後に 1 回の広い読み出しでコピーしていて、その読み出しにはストアバッファからの転送が効かず、演算そのものより高くついていました(インタプリタのサイクルで `objects` -32%、`dispatch` -24%、`loop` -27%、`collections` -18%、`fib` -14%)。各命令はソース行を持つので、例外は(タスクごとに)`file:line:in name` 形式のバックトレースを持ち、`__LINE__` も解釈実行・コンパイル済みの両方で動きます。

- **アロケータは、32 KiB 未満のブロックには mimalloc、それ以上にはシステムの `malloc` を使います**。`quarz` でも、コンパイル済みのプログラムでも使います(ランタイムのライブラリに含まれます)。参照カウント方式のランタイムは割り当てと同じだけ解放し、その多くは小さなブロックで、mimalloc はまさにこの使い方(Koka と Lean)のために設計されたものです。一方、大きなブロックを伸ばすとき、glibc はその場で伸ばすかページを付け替えますが、mimalloc はコピーします(追記で育てる配列や文字列。コンパイル済みの `collections` ベンチマークは mimalloc だけなら 20.5ms、この振り分けで 16.3ms です。どちらのアロケータのブロックかは、解放のときに一緒に戻ってくる大きさで決まります)。`QUARZ_ALLOC=system` でシステムの `malloc` を選べます(最初の割り当ての時点で一度だけ読みます)。mimalloc が要求する Transparent Huge Pages は、`QUARZ_THP=1` のときだけ使います(Go、JVM、glibc の `malloc` と同じです。カーネルは 2 MiB ずつゼロで埋めるので、プロセスごとに約 0.5ms 増え、大きなブロックをシステムのアロケータから取る今では、どのベンチマークも速くなりません)。`mimalloc` feature を外してビルドする(`cargo build --no-default-features`)と含まれません。システムのもの(glibc 2.36)と比べると、`quarz run` で `p 1` は 5.4ms から 4.9ms、解釈実行のベンチマークはサイクル数が 1〜5% 減ります(チャネルのピンポンで 4%、spawn/await で 5%)。コンパイル済みのものは 0〜5% 減ります。多数のタスクを使う場合の最大メモリ使用量は 2〜18% 増えます。これにはオブジェクトをフィールドの数どおりの大きさにすること(下記)が必要でした。すべてのオブジェクトが同じ大きさだったときは、`objects` ベンチマークの短命な `Vec2` と粒子が同じサイズの種類を使い、解放した領域をすぐには使い回さない mimalloc では粒子がそれらの間に散らばりました(L1 ミスが 7 倍、サイクル数はシステムのものより 5% 多い)。
- **タスクはスタックフルなコルーチン(`corosensei`)で、ワーカースレッドが動かします(M:N)。ワーカーの数は `QUARZ_THREADS` で、既定はプロセスが使える CPU の数です(アフィニティと cgroup の上限を考慮します。Go の `GOMAXPROCS` と同じです)**。スケジューリングは協調的で、チャネル操作、`sleep`、`await`、`Task.yield`、`loop` の中、I/O の待ちで切り替わります。ソケットはスケジューラの epoll/kqueue のリアクタで待ち、ファイル全体の操作、ディレクトリとメタデータの操作、名前解決、子プロセス、開いた `File` と標準入力の読み書きのうちバッファで済まないものは補助スレッドで実行して、呼んだタスクだけが待ちます。`Task.blocking { }` はブロックを別スレッドの 2 つ目のインタプリタで実行し、不変な値だけが行き来します。標準出力と標準エラーへの書き込みは同期的です。各タスクは仮想メモリ 16 MiB(メインタスクは 256 MiB)のスタックを予約し、超えると `SystemStackError` になります。デッドロック(全タスクが待機し、タイマーも保留中の I/O もない)は `DeadlockError` でプログラムを停止します。
- **ワーカースレッド。** 各ワーカーは自分のインタプリタを持ち、共有の `Program` と `Global` の上で動きます。`Program` は読み込んだプログラムから作るもので、`Send + Sync` です(コンパイル時に検査します)。`Global` は実行中のプログラムが積み上げる状態です。シンボル表(読み書きロックの中にあり、各インタプリタは引いた名前の写しを手元に持ちます)、定数(値が決まった後はロックなしで読めるセルで、初期化子は一度だけ実行され、その間ほかのタスクは待ちます)、フィールドのない enum の値、`at_exit` のブロック、標準出力がここにあります。ワーカーのインタプリタは、そのワーカーに初めてタスクが置かれたときに、そのスレッドの上でプログラムの写しから作ります。ワーカーはそれぞれ実行キュー、タイマー、epoll の reactor、タグの範囲を持ちます。新しいタスクは各ワーカーに順に置かれ、そこにとどまります(コルーチンとその下のネイティブのフレームはスレッドに結びついています)。work stealing はまだありません。タスクはほかから「ワーカーとその中の番号」で指されます。別のワーカーのタスクを起こすときは、そのワーカーの受信箱に入れて reactor を起こします。あるタスクから別のタスクに渡る値(チャネルで送る、`Task.spawn` で捕捉する、`Atom` に入れる、タスクが返す)は、参照先も含めて「共有」の印が付き、共有された値の参照カウントだけを原子的に更新します(`rc.rs`。共有された割り当て領域は 1 語目が 0 で、カウントは 2 語目にあるので、コンパイル済みコードは 1 語だけを読みます)。定数、トップレベルの `self`、enum の値は不死で、参照カウントを更新しないので、それらを使うワーカーどうしがキャッシュラインを奪い合いません。タスクが共有するものは、状態をロックの中に持ちます。チャネルはスピンロック(ワーカーが 1 つの間は、取得も普通の書き込みです)、タスクのハンドルは原子変数とロック、`Atom` の値と IO ハンドルの状態は mutex の中です。ソケットは、そのソケットを待つタスクがいるワーカーごとに、そのワーカーの poller に登録します。デッドロックは、どのワーカーにも実行できるタスク、タイマー、IO がなく、どのワーカーへ向かっているものもない状態です。メインのワーカーが、自分のタスクを挙げて報告します。プログラムはメインのタスクで(またはどれかのタスクの `exit` で)終わり、ほかのワーカーは止まります(そのタスクは巻き戻しません)。REPL と `Task.blocking` のヘルパースレッドは、ワーカー 1 つで動きます。`fib(27)` を計算する 8 つのタスクは、ワーカー 1 つで 0.33 秒、4 つで 0.12 秒です。echo のベンチマークでは、ワーカー 4 つで 16 接続のとき Go の 4 スレッドと同じ往復数を、64 と 256 接続では約 90% を処理します(bench/net/README.md)。ワーカーが 1 つのとき、2 つのタスクの間の 20 万回の往復は、ワーカーを入れる前より命令数が 3% 多くなります。
- **REPL**(`quarz repl`)は宣言・変数・実行中のタスクを入力をまたいで保持し、各入力を累積したプログラムに対して増分で検査します。クラスやメソッドの再定義はエラーです(新しい名前を使ってください)。§7 のホットリロードは未実装です。`require` と `require_relative` は REPL でも使え、読み込んだファイルのトップレベルを一度だけ実行します。行の編集には rustyline を使います(Emacs と vi のキー操作、`Ctrl-R` の履歴検索。`Ctrl-C` は入力中の内容を捨て、`Ctrl-D` で終了します)。終わりのない入力(閉じていないブロック、括弧、文字列)は同じ入力のまま次の行に続くので、定義はまとめて編集でき、履歴からもまとめて呼び出せます。次の行は、プロンプトの幅だけの空白で始まります。空白は入力の一部です(rustyline は 2 行目以降にプロンプトを出さないため)。これでコードの位置が揃います。ただし、文字列の途中では空白が中身を変えてしまうので入れません。履歴(1000 件)は `~/.quarz_history` に保存します。入力中の内容は、字句解析器のトークンに基づいて色付けします(`NO_COLOR` が設定されていれば色を付けません)。Tab キーで、セッションが知っている名前を補完します。ローカル変数、トップレベルのメソッド、キーワード、定数です。ドットの後では受け手の型のメソッド(ローカル変数の宣言された型、クラス自身のメソッド、リテラルのクラス。型が分からなければすべてのメソッド)、`::` の後ではクラスやモジュールの定数を補完します。
- **cog**([10-cogs.ja.md](10-cogs.ja.md))。`quarz-cog` が `Cog.toml` と `Cog.lock` を読み、最小バージョン選択でバージョンを解決し、`git` コマンドで各リポジトリをキャッシュにミラーし(必要なコミットだけを取得)、ロックされたコミットのツリーを読み取り専用で書き出してロックの内容ハッシュと照合します。`quarz-types` は各 cog の `src/` のファイルをすべて(依存先から)読み込み、ライブラリ cog のファイルを、トップレベルのどこにも登録されないそのルートモジュールの本文として検査します。各 cog は依存をマニフェストのキーで見て、ライブラリはアプリケーションの名前を見ません。プログラムが名指しする標準ライブラリのモジュール(`JSON`、`TCPSocket`)は `require` なしで読み込みます(スクリプトと REPL でも)。

を残します)。生成器は小さな命令ビルダのトレイトに対して書かれています。ムーブ・即値・分岐・`Int`/`Float`
