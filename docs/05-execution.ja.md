# 実行モデル: インタプリタと AOT コンパイラ

Quarz は 1 つのフロントエンドと 1 つのランタイムを、2 つのバックエンド(バイトコード VM と機械語)で共有します。開発中は `quarz run` で起動の速さと REPL を、本番は `quarz build` で実行速度を取り、**両者の観測可能な挙動は同一**です。

```
                    ┌────────────┐   ┌──────────────┐   ┌───────────────┐
  foo.qz ─────────▶ │ 字句・構文 │─▶ │ 名前解決・型 │─▶ │  QIR(型付き  │
  (+ .qzi 依存)     │   解析     │   │   検査       │   │   中間表現)   │
                    └────────────┘   └──────────────┘   └───────┬───────┘
                                                                 │
                       ┌─────────────────────────────────────────┼─────────────────────┐
                       │ quarz run / repl                        │ quarz build          │
                       ▼                                         ▼                      │
               ┌───────────────┐                     ┌────────────────────┐             │
               │ レジスタ VM   │                     │ 最適化(脱仮想化、 │             │
               │ バイトコード  │                     │ インライン化、RC   │             │
               │ (遅延生成)    │                     │ 省略、非ボックス化)│             │
               └───────┬───────┘                     └─────────┬──────────┘             │
                       │                                       ▼                        │
                       │                             ┌────────────────────┐             │
                       │                             │ LLVM IR → 機械語   │             │
                       │                             └─────────┬──────────┘             │
                       ▼                                       ▼                        │
               ┌──────────────────────────────────────────────────────────┐             │
               │  libquarz ランタイム(参照カウント、スケジューラ、永続   │ ◀───────────┘
               │  コレクション、文字列、多倍長整数、IO、チャネル、正規表現)│
               └──────────────────────────────────────────────────────────┘
```

## 1. コマンド

| コマンド | 動作 |
|---|---|
| `quarz run app.qz [args]` | 型検査してバイトコードで実行。依存ファイルの型検査結果はキャッシュ(`.quarz/cache`)される |
| `quarz repl` | REPL。入力ごとに型検査し、定義を追加できる(再定義は不可、代わりに新しい名前を使う) |
| `quarz check app.qz` | 型検査のみ |
| `quarz build app.qz -o app` | ネイティブ実行ファイルを生成。`--release` で最適化、`--dev` で高速コンパイル(最適化なし) |
| `quarz test` | `test/**/*_test.qz` を実行 |
| `quarz fmt` | 整形 |
| `quarz pkg add json` | パッケージ管理。マニフェストは `Quarz.toml` |

## 2. コンパイル単位と分割コンパイル

- 1 ファイル = 1 コンパイル単位。各単位の型検査結果から**インターフェースファイル** `.qzi`(クラス・メソッドのシグネチャ、フィールドのレイアウト、定数の型、`extension` の一覧、インライン化候補の小さなメソッドの QIR)が生成されます。
- 依存する単位は `.qzi` だけを読みます。引数型が必須なのはこのためで、本体の変更は(シグネチャが変わらない限り)他の単位の再コンパイルを引き起こしません。
- `quarz build` は最終段でプログラム全体の QIR を集めて、クラス階層解析(CHA)による脱仮想化とクロスモジュールのインライン化を行います。クラスが実行時に作られないため、CHA は完全です。
- 標準ライブラリは事前に `.qzi` + ネイティブ(`libquarz-std`)として配布され、`quarz run` でも最初から機械語で動きます。

## 3. QIR

QIR は型付きの SSA 形式の中間表現です。Ruby 風の構文は QIR に落ちる段階で単純化されます。

- メソッド呼び出しはすべて解決済み(`call Account#deposit`、`vcall Shape#area`、`icall Comparable#<=>`)。
- エスケープしないブロックはインライン展開または静的なローカル関数呼び出し。`break`/`next`/`return` はジャンプに変換。
- `case/in` は決定木。
- 合併型の値は `(tag, payload)`。絞り込みは `tag` の検査。
- `Int` の演算は「あふれ検査付きの 63 ビット加算 → あふれたら多倍長ルーチン」に展開。
- 参照カウントの `inc`/`dec` が明示的に挿入され、以後の最適化パスで省略される。
- 安全点(`safepoint`)命令が、ループの後方分岐とメソッド入口に挿入される。

インタプリタとコンパイラの意味論が一致する根拠は、どちらも同じ QIR を入力にし、同じランタイム関数を呼ぶことです。QIR から先で許される差は性能だけで、CI では同じテストスイートを両モードで実行して差分検査(differential testing)を行います。

## 4. インタプリタ

- **レジスタ VM**。QIR の各 SSA 値がレジスタに対応し、型が静的に分かるので、`Int`/`Float`/`Bool` はボックス化せずにレジスタに置かれます。
- バイトコードはメソッドが初めて呼ばれたときに QIR から生成します(遅延コンパイル)。起動時にやるのは構文解析と型検査だけで、キャッシュが効いていれば数十ミリ秒で動き始めます。
- ディスパッチは direct threading。`Int#+` や `Array#[]` のような頻出操作は専用命令を持ちます。
- 型情報があるため、動的言語のインタプリタに必要なインラインキャッシュやガードがありません。目標は Lua/LuaJIT インタプリタ級の速度で、Ruby(YJIT なし)の 3〜10 倍程度を想定しています。
- 将来、ベースライン JIT(QIR → 機械語をその場で生成)を追加できますが、「本番は AOT」を前提にしているため優先度は低く置いています。

## 5. メモリ管理

**参照カウント(RC)+ 一意性による在場更新 + 可変オブジェクト限定のサイクル回収**を採用します。

### なぜ参照カウントか

1. **不変値の在場更新**: 参照カウントが 1 の不変値は、「新しい値を返す」操作をその場で破壊的に行えます(Lean 4 / Koka の Perceus)。Quarz の「不変を既定にしつつ速い」はこれに依存しています。
2. **AOT との相性**: トレース GC はネイティブコードのスタックマップ(LLVM statepoint など)か保守的スキャンが必要で、実装の難所です。RC はどちらも不要で、C FFI との境界も単純です。
3. **停止時間がない**: スケジューラが多数のタスクを動かすとき、GC のストップ・ザ・ワールドは応答性を損ないます。
4. **決定的な解放**: `ensure` と組み合わせて、ファイルハンドルなどの資源を予測可能に解放できます。

### 詳細

- **非原子的カウントが既定**。タスク境界を越えた値(チャネル送信、`spawn` の捕捉、`Atom`、定数)は、その時点でオブジェクトグラフをたどって「共有済み」ビットを立て、以後は原子的操作になります。すでに共有済みの部分グラフは再走査しません。不変値は共有済み後も内容が変わらないため、これ以外の同期は不要です。
- **RC 省略**: 借用推論(引数として渡すだけで保持しない参照に `inc`/`dec` を挿入しない)と、`inc` の直後の `dec` の相殺。
- **再利用**: `dec` でちょうど 0 になった直後に同じサイズの割り当てがあれば、メモリを再利用します(`data` の `with` や `Array#push` が割り当てなしで済む)。
- **サイクル回収**: 不変値は作られた時点で自分より古い値しか指せないので、サイクルを作れません。サイクルを作りうるのは `var` フィールドを持つオブジェクトと、再代入される捕捉変数のボックスだけです。これらのオブジェクトだけを候補として、Bacon–Rajan の試行削除を低頻度で走らせます。ほとんどのプログラムでは候補集合が小さく、回収コストは無視できます。
- **`Int` の小さな値、`Float`(型が静的なとき)、`Bool`、`Nil`、`Symbol`** はカウント対象外です。
- **弱参照**は提供しません(必要になる状況が可変オブジェクトのサイクルに限られ、サイクル回収で解決するため)。

### 採用しなかった案

- **世代別トレース GC(Go/Erlang/Ruby)**: 割り当てが速く、カウント操作のオーバーヘッドがありませんが、上の 1〜3 を失います。不変値の在場更新ができないと、永続データ構造のコストを常に払うことになります。
- **原子的 RC を常時(Swift)**: 単純ですが、原子的操作のコストが全体にかかります。Lean 4 方式の「共有された部分グラフだけ原子的」は、タスク境界が明示的な Quarz に適合します。

## 6. ネイティブコード生成

- `--release` では QIR → LLVM IR(`inkwell`)。`--dev` では Cranelift でビルドの速さを優先します。
- `Int` のあふれ検査は `llvm.sadd.with.overflow`、`Float` は非ボックス、`data` の小さなインスタンスはスカラー置換により構造体として扱われます。
- 例外は Itanium ABI のゼロコスト例外(landing pad)。`rescue` のない経路にはコストがありません。
- タスクのスタックは `mmap` で予約されるため、スタック切り替えは SP の差し替えだけです(アセンブリ数十行の `switch_context`)。
- 出力は静的リンクされた単一バイナリ(libquarz を含む)。`--shared` で共有ライブラリも作れます。

## 7. REPL と開発時の体験

- `quarz repl` は入力を型検査してからバイトコードで実行します。`class` や `def` を対話的に追加でき、既存の定義を変えたいときは REPL が「その定義を使っているものごと」再コンパイルして差し替えます(ホットリロード)。これは REPL だけの機能で、プログラムの意味論には影響しません。
- 型エラーは Ruby 風の位置表示に、期待型と実際の型、絞り込みのヒント(「ここで `x` は `String?` です。`if x` で絞り込めます」)を添えて出します。
- `quarz run --watch` でファイル変更時に再実行。

## 8. 実装言語と構成

実装言語は **Rust** です。フロントエンド、VM、ランタイムをすべて Rust で書き、`cargo build` で単一バイナリ `quarz` を得ます。

### なぜ Rust か

Quarz の実装で最初から必要になるものを並べると、Rust のエコシステムで埋まる部分が多いことが決め手です。

| 必要なもの | Rust での手当て |
|---|---|
| スタックフルなタスクの切り替え | `corosensei` |
| ワークスティーリングスケジューラ、チャネル | `crossbeam` のデック・同期プリミティブ。競合の検出をコンパイラに任せられる |
| 非同期 IO | ソケットは `polling`(epoll/kqueue)、ファイル IO と子プロセスは補助スレッド |
| 多倍長整数、正規表現、Unicode | `num-bigint`(または `rug`)、`regex`、`unicode-*` |
| 永続ベクタ・HAMT | RC の一意性で在場更新するため自前。`im`/`rpds` を参考にする |
| AST・型の処理 | `enum` とパターンマッチ |
| 後のバックエンド | Cranelift は Rust ネイティブ、LLVM は `inkwell` |

検討した他の候補:

- **C**: CRuby と同じ流儀で書けるが、上の表のライブラリ群を vendor する手間と、スケジューラ・チャネルという最もバグを出しやすい部分を安全装置なしで書くことになる点で見送り。
- **OCaml(フロントエンド)+ C(ランタイム)**: 型検査器を書くには最良だが、Quarz の本体はランタイム寄り(RC、スケジューラ、在場更新)で、そこと型検査器を別言語にするとインタプリタの起動パスが複雑になる。
- **Zig**: ランタイムには向くが、言語と標準ライブラリの安定性が不足。
- **Ruby で stage0 を書き、早期にセルフホスト**: Quarz への移植は楽だが、`quarz run` のたびに Ruby で型検査することになり、開発用インタプリタとしての起動の速さを失う。セルフホストは必須ではなく、やるとしても Rust 実装が安定した後とする。

### Rust で書く上での方針

- **`unsafe` はランタイムに閉じ込める。** タグ付きポインタ、RC の非原子/原子切り替え、在場更新は Rust の所有権モデルの外側にあり、ここは「Rust で書く C」になる。`quarz-rt` の内部だけに `unsafe` を置き、VM とフロントエンドには安全な API だけを見せる。
- **AST と型は arena で持つ。** `Rc<RefCell<_>>` の木は作らず、`Vec` + `NodeId(u32)`/`TypeId(u32)` の index で参照する。借用検査との衝突を避け、QIR への変換やキャッシュの直列化も単純になる。
- **構文解析器は手書きの再帰下降。** Ruby 系の文法は字句解析器が状態を持つ(`{` のブロック/ハッシュ、`name: Type` のラベル、ヒアドキュメント、文脈キーワード)ので、Prism と同じく手書きが向く。
- **クレートを分けてコンパイル時間を局所化する。**

### クレート構成

```
quarz/
  Cargo.toml          ワークスペース
  crates/
    quarz-syntax      字句・構文解析、AST(位置情報付き)、エラー報告
    quarz-types       名前解決、型検査、Shareable 導出、.qzi の読み書き
    quarz-ir          QIR(レジスタマシン IR)と実行時メタデータ(RtWorld)
    quarz-lower       型検査済み AST → QIR
    quarz-rt          オブジェクトモデル、RC、永続コレクション、文字列、多倍長整数、
                      スケジューラ、チャネル、IO(unsafe はここだけ)
    quarz-vm          ランタイム(オブジェクトモデル、RC、スケジューラ、チャネル、IO、ネイティブ)と QIR インタプリタ。
                      コンパイル済みプログラムがリンクする静的ライブラリでもある
    quarz-aot         QIR → 機械語(Cranelift)とリンク
    quarz-cli         quarz run / check / repl / fmt
  std/                標準ライブラリ(Quarz で書く部分)
  docs/
  examples/
```

### 実装の順序

1. `quarz-syntax`: 字句解析器、構文解析器、AST。`examples/` が構文解析を通ることを目標にする。
2. `quarz-types`: 名前解決と型検査。まず単相のクラス・メソッド・合併型・フロー型付け、次にジェネリクス、`data`/`enum`、パターンの網羅性、`extension`。
3. `quarz-rt` の最小部分: オブジェクトモデルと RC、`Int`/`String`/`Array`/`Hash`。
4. `quarz-vm`: QIR とレジスタ VM。`quarz run` で `examples/hello.qz` と `shapes.qz` を動かす。
5. `quarz-rt` の並行部分: タスク、スケジューラ、チャネル、`Atom`、非同期 IO。`wordcount.qz`、`pipeline.qz`、`bank_actor.qz` を動かす。
6. 標準ライブラリの拡充、REPL、`.qzi` による分割コンパイルとキャッシュ。
7. ネイティブバックエンド(Cranelift で `--dev`、LLVM で `--release`)。
8. パッケージ管理、`fmt`、LSP。

## 9. 現在の実装(v0.0.1)

現時点の実装は、上の計画と意図的にいくつかの点で異なります。計画は引き続き設計の向かう先を示しています。

- **プログラムは QIR に下げられ、レジスタ VM が解釈します**。型検査器が木に型、解決済みの呼び出し先、変数スロットを付け、`quarz-lower` がメソッド・ブロック・定数初期化子・ファイルのトップレベルをそれぞれ QIR の関数にし(`quarz ir FILE` で表示できます)、`quarz-vm` がそれを実行します。ブロックに捕捉されるローカル変数はヒープ上のフレームに、それ以外はレジスタに置きます。キーワード引数はランタイムが束縛し、デフォルト値は呼ばれた側のプロローグで評価します。ブロックからの `break`/`return` はランタイムを通るステータスコードで、`ensure` はあらゆるフローを受けて再開するハンドラブロックです。`ensure` 領域を抜ける通常の `return`/`break` は本体をインライン展開して実行します。`Int`/`Float` の演算子と自動生成のフィールドアクセサはメソッドディスパッチを迂回します。各命令はソース行を持つので、例外は(タスクごとに)`file:line:in name` 形式のバックトレースを持ち、`__LINE__` も解釈実行・コンパイル済みの両方で動きます。`bench/` のプログラムはリリースビルドでそれぞれ 0.15〜0.85 秒です(`fib(27)`: 0.18 秒、3M 回のカウントループ: 0.47 秒)。
- **値は `Rc` ベースです**。不変コレクションは `Rc<Vec>` / `Rc<IndexMap>` で、更新は `Rc::make_mut` により参照が一意でなければコピーします。15 バイト以下の文字列は値そのものの中に置かれます(割り当ても参照カウントもなく、コピーは 3 語のコピーです)。それより長い文字列は共有の `Rc<str>` です。どちらかで観察できる違いはありません(`==`、`equal?`、ハッシュ、順序はテキストを比較します)。評価器は `xs = xs.push(x)` という頻出形でレシーバを変数から移動するので、この場合は在場更新になります。§5 の Perceus 流の一般的な再利用は今後の課題です。スケジューラが単一スレッドなので参照カウントは非原子的です。
- **タスクは 1 つの OS スレッド上のスタックフルなコルーチン(`corosensei`)です(M:1)**。スケジューリングは協調的で、チャネル操作、`sleep`、`await`、`Task.yield`、`loop` の中で切り替わります。各タスクは仮想メモリ 16 MiB(メインタスクは 256 MiB)のスタックを予約し、超えると `SystemStackError` になります。デッドロック(全タスクが待機し、タイマーもない)は `DeadlockError` でプログラムを停止します。タイマーはスレッドをスリープさせ、ファイルと標準入出力は同期的です。
- **REPL**(`quarz repl`)は宣言・変数・実行中のタスクを入力をまたいで保持し、各入力を累積したプログラムに対して増分で検査します。クラスやメソッドの再定義はエラーです(新しい名前を使ってください)。§7 のホットリロードは未実装です。`require` と `require_relative` は REPL でも使え、読み込んだファイルのトップレベルを一度だけ実行します。
- **`Bytes`・`Time`・`json` ライブラリ**。`Bytes` は不変のバイト列で、`b"..."` リテラル、`Bytes::Builder`、`String#to_bytes`/`encode`、`Bytes#decode`(UTF-8、ASCII、ISO-8859-1)を持ちます。`Time` は UTC オフセット付きの時刻(`Time.now`/`utc`/`local`/`at`/`parse`/`iso8601`、`strftime`、`Duration` との加減算)で、`Time.monotonic` は単調増加クロックを `Duration` で返します。`require "time"` は受け付けますが不要です。`require "json"` で `JSON.parse -> JSON::Value` が使えます。`JSON::Value` は `Null`・`Boolean`・`Integer`・`Number`・`Text`・`List`・`Map` の 7 つのバリアントを持つ enum で(それぞれ値を持ち、`as_s`・`as_i?`・`[]` などのアクセサがあります)、`JSON.generate`/`pretty_generate` と `to_json` も提供します。クラスは `to_json -> String` を定義すれば JSON 表現を変えられます。パーサと生成器はネイティブで、残りは Quarz で書かれています(`std/json.qz`)。
- **`quarz build` はネイティブ実行ファイルを生成します**。`quarz-aot` が QIR の各関数を Cranelift で機械語にします。ムーブ・即値・分岐・`Int`/`Float` の算術と比較(オーバーフローとゼロ除算の検査付き)はインライン化し、クラス階層解析でオーバーライドされないと分かるメソッドの呼び出しは(ブロック付きでも)ネイティブに直接向かい(`qz_call_static`)、コンパイル済みの本体なら本体そのものを直接呼びます。呼び出し側が自分のフレームに引数を並べ(非ボックス化された数値はタグと 1 語)、スタック上のバッファに呼び先の活性化レコードを組み立てます。呼び先がヒープフレームもメソッドタグも必要とせずブロックも受け取らない場合は、組み立て・コールスタックへの push・ネイティブスタックの検査・後始末・pop までをインラインで行い(`quarz_vm::layout` が公開するオフセットを使い、レイアウトの異なるランタイムではプログラムが起動を拒否します)、それ以外はランタイム(`qz_enter`/`qz_leave`)が行います。`yield` とコンストラクタは専用の入口を使います(全フィールドを与えられた data 型は、呼び出し元の引数領域に並べたフィールドからその割り当て内に直接構築します)。`x = x.push(v)` と `@items = @items.push(v)` はコレクションを変数やフィールドから取り出してその場で更新し(他に参照がなければコピーしません)、`Array`/`Hash`/`Set` のよくある更新は引数リストすら作りません。関数から出ない data 値(作って、フィールドごとに読んで、捨てる)は確保されず、そのフィールド読み出しはコンストラクタ引数のレジスタの読み出しになります。そのような data 型(フィールドがすべて `Int`/`Float`/`Bool`、01-syntax §4 参照)を型に持つフィールドは値をその場に保持し、物理フィールドをオブジェクト内に並べます(lowering は読み出しを構築に変換してスカラー置換がそれを取り除き、書き込みは成分ごとの格納になります)。粒子に格納される `Vec2` も割り当てを要しません。要素がすべて `Int` またはすべて `Float` の配列は要素を非ボックス化して(機械語の語として)格納し(それ以外の値が push されると格納はボックス化された値に切り替わります。切り替えは配列ごとに高々一度です)、配列の長さ、範囲内の添字による要素の読み出し(非ボックス化格納なら語の読み出しとタグの書き込み、ボックス化格納ならコピー)、余裕のある非共有配列への追加(`ArrayPush` と、ローカル変数・捕捉変数・フィールドに対する `xs = xs.push(v)`)は、ベクタ(その語の配置と格納の種別はランタイムが起動時に検査します)を通してインラインで行います。`self`、引数、捕捉変数(フレームのスロットビュー経由)、オブジェクトのフィールド(オブジェクトのフィールドビュー経由)の読み書きはインラインで、参照カウントの増減もインラインに行い、最後の参照を破棄するときだけランタイムを呼びます。小さなメソッド(フレーム・ハンドラ・ブロックを持たないもの。二段まで)は QIR 上で呼び出し元にインライン展開され、バックトレースでは出所の表からその呼び出し先のフレームを復元します。両方のレジスタがコピーした値を保持している間しか読まれないレジスタのコピーはコピー伝播で取り除きます(インライン展開と引数の束縛が作るコピーは、それぞれ参照カウントの増減一回分でした)。フィールドへの格納・配列への追加・data 型の構築・直接呼び出しの引数がレジスタを最後に読む場合は、コピーせずにそこへムーブします。`Int`・`Array`・リテラルの `Int` 範囲に対する `times`、`upto`、`each`、`each_with_index`、`map`、`select`、`reject`、`reduce`、`count`、`any?`、`all?` のブロックは、入れ子のものがその変数を捕捉していなければ、その場でカウントループとして lowering されます(`break`/`next` はジャンプ、変数はレジスタ、ブロック内の局所変数は反復ごとに nil に戻ります)。クロージャは作られず、要素ごとの呼び出しもありません。データフロー解析で「機械語に収まる `Int`」「`Float`」「`Bool`」を保持すると分かるレジスタは SSA 変数に非ボックス化され、その算術にはタグ検査がありません。lowering が記録した演算子の多重定義(`Int#+(Int)`)から被演算子の型が分かり、`Int`/`Float` と宣言された引数は読み出し時に一度だけ検査し、そう宣言されたフィールドは非ボックス化変数へ直接読み出し(タグはオブジェクト内で検査し、合わなければその読み出しをインタプリタでやり直します)、状態が不明な被演算子も実行時に一度だけ検査し、投機が外れたとき(BigInt だった、溢れた、ゼロ除算)はその活性化の残りをインタプリタに引き渡します(`qz_resume`)。非ボックス化されたレジスタがメモリ上のボックスに書き戻されるのは、メモリが読まれる場所(ランタイム呼び出し、ハンドラ、その引き渡し、ボックス化された値を期待するブロック)だけで、生存解析によってまだ必要なレジスタに限られます。レジスタの初期化と解放はインラインで、`return` はその時点の状態でヒープ値を持ち得るレジスタだけを解放します。`Int`/`Float` の `==`/`!=` はインラインの比較で、結果が読まれないその場更新(文としての `xs = xs.push(v)`)は結果を格納しません。短い文字列定数は値の 3 語をそのまま書き込み、長い文字列とシンボルの定数は専用のランタイム入口で関数のプールから複製します。文字列補間にも専用の入口があります。それ以外の命令はランタイム(`qz_exec`)を呼んでコンパイル済み関数のレジスタ上で実行します。例外と `ensure` の経路はコンパイルされます。反復するネイティブ(`each`、`map`、`select`、`times`)と `yield` は、ブロックの活性化レコードを一度だけ用意して呼び出しごとに使い回します。よく使うネイティブ(`String#size`/`==`/`end_with?`/`upcase`/`+`、`String::Builder#<<`、`Array#size`/`[]`、`Hash#[]`/`key?` など)には、レシーバと引数をレジスタから参照で受け取る版があり(引数リストもコピーもなし)、コンパイル済みの呼び出し・インタプリタ・`&:name` の proc(直前のレシーバのクラスで見つけたメソッドをキャッシュし、反復するネイティブからは引数リストを作らずに呼ばれます)から使われます。文字列補間、`upcase`、`+`、`Int#to_s` は使い回すバッファに結果を組み立てる(整数はランタイム自身の十進変換で)ので、それぞれ割り当ては高々一回、短い結果なら零回です。実行ファイルにはシリアライズしたモジュール(ランタイムがクラス・メソッド表を必要とし、機械語のない関数は解釈実行するため)を埋め込み、システムの `cc` で `libquarz_vm.a` を静的リンクするので、コンパイル済みプログラムと `quarz run` は 1 つのランタイムを共有し同じ挙動になります(テストスイートが全サンプルをコンパイルして比較します)。コンパイル済みプログラムの起動は約 2 ms(半分はカーネルと動的ローダ)で、埋め込みモジュールのデコードとメソッド表の構築には高速なハッシュを使い、終了時には何も解放しません。`--release`/`--dev` の区別はまだなく、局所的な数値以外の値はボックス化されたままなので、Go や Rust との残りの差(4〜30 倍。`bench/compare/` 参照)はタグ付き・参照カウント付きの値表現、すべてのオブジェクトがヒープに確保されること、残った呼び出しの規約によるものです。`bench/` ではカウントループが VM の 40〜60 倍(0.55 秒 → 0.009〜0.014 秒)、`fib(27)` が 19 倍(0.15 秒 → 0.008 秒)、コレクションのベンチマークが 15 倍(0.49 秒 → 0.032 秒)、オブジェクトのベンチマークが 14 倍(0.10 秒 → 0.007 秒)、文字列のベンチマークが 2.4 倍(0.076 秒 → 0.031 秒)です。

- **実装中に決めた細かい事項**(他の章を設計のまま保つためにここにまとめます): `*rest` の後ろの引数はキーワード専用(`*` 単独の後ろと同様)。`[]?` はメソッド名(`xs[i]?`)。`x in pattern` は引数リストの中でも書ける。配列リテラル同士の `[a, b] <=> [c, d]` はタプルとして要素ごとに検査する。複数の引数を宣言したブロックが 1 つの配列またはタプルを受け取ると Ruby と同様に展開する。`Object` は `Kernel` を `include` し、`puts` は全オブジェクトのプライベートメソッド。`IO` ハンドルは `Shareable`(ランタイムがアクセスを直列化する)。prelude は組み込みを `native def` で宣言する。`Comparable#clamp` はネイティブで `self` を返す。`case/in` の異なるアームで束縛されるパターン変数は別の変数。合併型・`data`・`enum`・`Nil`・`Bool` の選択肢を取りこぼす `case/in` はエラー、`Int` のような開いた型の値の取りこぼしは警告(実行時は `NoMatchingPatternError`)。型テストで主題を覆う `case/when` に `else` は不要。`break` のない `loop` の型は `Nothing`。浮動小数点数は Ruby と同じ形式で表示する。`Hash` のキーと `Set` の要素は、不変の組み込み値と `data`/`enum` の値については構造的等価、クラスのインスタンスについては同一性で比較する(キーの比較にユーザー定義の `==`/`hash` は使われない)。サブクラスや enum のバリアントがオーバーロードされたメソッドの一方だけをオーバーライドした場合、他方に解決された呼び出しはスーパークラス側に届く(ランタイムは名前だけでなくシグネチャでディスパッチする)。
