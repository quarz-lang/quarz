# Execution Model: Interpreter and AOT Compiler

Quarz shares one front end and one runtime across two back ends (an interpreter of the QIR and machine code). During development, `quarz run` gives fast startup and a REPL; for production, `quarz build` gives execution speed; and **the observable behavior of the two is identical**.

```
                    ┌────────────┐   ┌──────────────┐   ┌───────────────┐
  foo.qz ─────────▶ │ Lexing and │─▶ │ Name resol.  │─▶ │  QIR (from    │
  (+ required files)│  parsing   │   │ & type check │   │ checked code) │
                    └────────────┘   └──────────────┘   └───────┬───────┘
                                                                 │
                       ┌─────────────────────────────────────────┼─────────────────────┐
                       │ quarz run / repl                        │ quarz build          │
                       ▼                                         ▼                      │
               ┌───────────────┐                     ┌────────────────────┐             │
               │ QIR           │                     │ Optimization       │             │
               │ interpreter   │                     │ (devirtualization, │             │
               │               │                     │ inlining, RC       │             │
               └───────┬───────┘                     │ elision, unboxing) │             │
                       │                             └─────────┬──────────┘             │
                       │                                       ▼                        │
                       │                             ┌────────────────────┐             │
                       │                             │ LLVM IR → machine  │             │
                       │                             │ code (clang)       │             │
                       │                             └─────────┬──────────┘             │
                       ▼                                       ▼                        │
               ┌──────────────────────────────────────────────────────────┐             │
               │  libquarz runtime (reference counting, scheduler,        │ ◀───────────┘
               │  copy-on-write collections, strings, bignums, IO,        │
               │  channels, regular expressions)                          │
               └──────────────────────────────────────────────────────────┘
```

## 1. Commands

| Command | Behavior |
|---|---|
| `quarz run app.qz [args]` | Type-check (reusing the checks of unchanged files, §2), lower to QIR and interpret it |
| `quarz repl` | REPL. Each input is type-checked, and definitions can be added (redefinition is not allowed; use a new name instead) |
| `quarz check app.qz` | Type-check only; `--expand` prints what the class bodies' `static` statements generated ([14-metaprogramming.md](14-metaprogramming.md) §5); `--tree` prints the checked syntax tree, with each node's type, as JSON (for the differential tests of `formal/`: the format changes without notice) |
| `quarz build app.qz -o app` | Produce a native executable, optimized through LLVM |
| `quarz ir app.qz` | Print the QIR of every function (for debugging the lowering); `quarz tokens` and `quarz parse` print the tokens and the syntax tree |
| `quarz test` | Run `test/**/*_test.qz`, or the test files given: Test::Unit-style classes found by the compiler ([12-testing.md](12-testing.md)); `--release` compiles them |
| `quarz doc [NAME]` | Print a declaration's documentation, or generate a cog's site (`--html`), from the comments above declarations ([13-doc-comments.md](13-doc-comments.md)); `quarz test` runs the examples in them |
| `quarz --version` | Print `quarz` and the workspace's version from `Cargo.toml` (`quarz 0.0.1`); a release is tagged `v` and that version |
| `quarz fmt` | Format (*planned*) |
| `quarz cog add <git-url>` | Package management: a cog is a git repository pinned to a commit in `Cog.lock`; the manifest is `Cog.toml` ([10-cogs.md](10-cogs.md)). `run`, `check`, `build` and `ir` take an application (a directory with a `Cog.toml`, its `src/main.qz`, or nothing for the one around the current directory) as well as a script |

## 2. Compilation Units and Separate Compilation

One file is one compilation unit. What is done separately, per unit and kept between runs, is checking; everything after it (lowering's optimizations, code generation) sees the whole program. The language's rules make a file's check independent of the files after it: a top-level `extension` is active only in the cog or program that declares it (01-syntax.md §7), `==` narrows only types that cannot be subclassed (02-types.md §6), `nil?` and `is_a?` cannot be redefined (01-syntax.md §3), a `data` type's layout is decided where it is defined, and return types are declared, not inferred (02-types.md §5). Two things rest on this independence. The prelude and the standard library are checked when `quarz` is built, before any program exists: a program's extensions, subclasses with their own `==`, or redefinitions of `nil?` could otherwise change what their bodies' checks found. And a file's kept check is keyed by the other files' declarations without their bodies, which works because everything a call needs from a method, its return type and whether it keeps its block, is in the signature. (Whether a class may inherit from a built-in value class is a different matter: their values are the runtime's own, so a subclass's objects could not be used as them.) A unit's QIR does not depend on the units after it either: what class hierarchy analysis rewrites (a field reader nothing overrides becomes a field read, `new` in a class method on a class with no subclass a plain construction) is done once the program is linked, and a field's default is lowered once, by the class that declares it.

**The prelude and the standard library.** They are declared and checked when `quarz` is built, and a command starts from that state, encoded in its executable (`quarz_types::PreludeState`, by `quarz-cli/build.rs`; `QUARZ_NO_PRELUDE_CACHE=1`, not `0`, checks them from their sources). The prelude's state is one; the standard library's modules are checked in the sets programs load (`json`; `time`; `socket`; `json`, `socket` and `http`; `test`), each set a state with those modules as the program's first units, with fixed unit numbers (`load::std_unit`) so that their numbers are the same in every program. A program that loads another mix checks the modules from their sources. The standard library's exports are read from its declaration lines rather than by parsing it. Its methods, like the prelude's, are lowered only once something may call them (§9). `puts 1` took 121.6M instructions and takes 23.2M.

**Compile-time execution.** A class body's `static` statement ([14-metaprogramming.md](14-metaprogramming.md)) runs during the check, after every file is declared and before the bodies are checked: the compiler lowers the `static def` it calls and what that reaches (checking those bodies on demand), refuses a reach into the natives that act on the outside world, and runs the statement on the interpreter, which the compiler installs for it (`quarz check` and `quarz build` too, not only `quarz run`; a compiled program still carries none of it). The statements run on every check, whether or not the file's results are read back, cog by cog in dependency order (a script file by file), each cog's before its files are keyed and read back: the members they generate (`def_method`) are declarations of the statement's file, part of its interface, so they exist when the kept checks that refer to them are read back, and a change in a dependency's `static def` that changes what it generates changes the file's key (a change that generates the same cannot affect the file's check: bodies are lowered again every time). A `static def` that reaches the reflection, or a `Meta::ClassDef`, is compile-time only, which the compiler decides after lowering it and reports at any call of it from ordinary code; the other `static def`s are ordinary methods too.

**A file's check, kept between runs (`quarz_types::cache`).** Checking adds to one world: classes, methods, constants, type aliases, extensions and type parameters are numbered in the order they are declared, and the checker's results are tables keyed by syntax node, numbered within the unit's range (`load::unit_base`). What checking a file's bodies recorded (the results for its nodes, its methods' frame sizes, its constants' types, the `Self`-construction sites, its warnings) is kept under a key made of the compiler's build, the file's syntax tree, every file's *interface* (`cache::interface`: each entity's declaration without bodies, defaults' and constants' values, or positions) (a cog's top-level `def`s, called from all its files, are declarations of their files' main classes, so their signatures are in it) and, in a movement, its cogs (names, root modules, dependency keys) and the file's own cog. On the next run the file is parsed and declared again (cheap), and when its key is unchanged its bodies are not checked: the kept results are read back, renumbered (`reloc`). Every number in them that refers to an entity says whose it is: the prelude's and the standard library's keep their numbers; another file's is written as that file (by its path) and the entity's position among that file's own, and reading back looks the position up in this program. Node ids and spans stay as they are: they are part of the file's syntax tree in the key, so a file read back is in the same range, and adding, removing or reordering a file loaded before it checks it again. So a change to a body re-checks that file alone; a change to a signature, a constant's initializer or an alias re-checks every file. Constants' types are inferred from their initializers, so they are not in the interfaces: they are compared after checking, and a mismatch checks the program again without the cache. Diagnostics come out in the order of files and positions, the same whether a file was checked or read back.

The cache is on by default and shared by every program a user runs, as Go's build cache and Crystal's are (`quarz run file.qz` runs a script in place: there is no project directory to keep it in, as Cargo's `target/` is). It is under `$XDG_CACHE_HOME/quarz` (`~/.cache/quarz`); `QUARZ_CACHE_DIR` moves it (the test suite's is under `target/`, from `.cargo/config.toml`) and `QUARZ_NO_CACHE=1` turns it off. Entries are written aside and renamed, carry a checksum (a damaged one is a miss), and an entry unused for 30 days is removed (looked for at most once a day, when one is written). On a fixture of a few hundred lines, `quarz check` goes from 26.0M instructions to 18.9M with its checks reused (writing them costs 2M the first time).

**What stays whole.** Units are checked separately, never compiled separately: lowering's optimizations and code generation always see the whole program, as Rust's crates carry MIR for their users to instantiate and inline. This is what lets every method be overridable without a `virtual` (or Swift's `open`, Kotlin's `open`) and still compile to direct calls: a unit compiled to machine code on its own would not know which of its methods a later unit overrides, so each call it makes on its own public methods would stay a dispatch, nothing it calls could be inlined, and shake (§9) could drop none of its methods. Since no classes are created at runtime, class hierarchy analysis is complete. The whole-program analyses are CHA, devirtualization, inlining, shake, the field layouts of `quarz_ir::field_slots` and monomorphization when it comes.

**Considered and not built.** An interface file (`.qzi`) per unit that holds its declarations and lowered QIR, read instead of parsing and declaring the file, and distributed for the standard library: parsing and declaring a file costs a few million instructions, and of lowering only the translation to QIR is per file (10M of 58M on the largest fixture; the passes after it are whole-program), so neither pays for the renumbering of QIR it would take. The standard library's checked state is embedded in the command instead. Whether `quarz run` should also get the library's Quarz methods as machine code (compiled on their own, so with the dispatches above, which an interpreter can afford) is open.

## 3. QIR

QIR (Quarz Intermediate Representation) is the intermediate representation both back ends take as input: a register machine (registers may be reassigned) with basic blocks, each block possibly covered by a handler block. The Ruby-like syntax is simplified at the point of lowering to QIR.

- Method calls are resolved where the checker can (a call names its method, dispatched on the receiver's class when a subclass overrides it); otherwise they are looked up by name at run time. Constructors, procedure calls, `yield` and `super` have their own call kinds.
- The blocks of the common iterators (`times`, `upto`, `each`, `map`, `select`, ... on `Int`, `Array` and literal ranges) are lowered in place as loops, `break`/`next` becoming jumps; other blocks are closures, and `break`/`return` out of them are status codes carried through the runtime. Small methods are inlined.
- Values are tagged (a union type needs no other representation), and `Int` arithmetic checks for overflow and raises `OverflowError` (an `Integer` holds any size).
- Reference counting and task switching are done by the runtime and by the code the back ends generate, not by QIR instructions. QIR does say where a value moves rather than being copied: a copy or call argument that is the register's last read moves the value (`Take`, a call's moved operands), so a collection passed on stays uniquely referenced. A variable whose release may be observed (03-data-model §4) is read last by a `Release` at the end of its scope, which releases it there and runs the `deinitialize` of what went; a pass then drops a `Release` that nothing between the variable's last use (a call it moves into) and the end of the scope could tell apart, number arithmetic and copies of other registers in between being transparent (Swift's deinit barriers), so the value moves into that call as before.
- After optimization, registers whose values are never live at once share a number (keeping apart those that may hold a counted value), so a method with inlined callees needs a dozen registers rather than a hundred.

The basis for the interpreter and compiler agreeing on semantics is that both take the same QIR as input and call the same runtime functions. The only difference allowed from QIR onward is performance, and CI runs the same test suite in both modes as differential testing.

Two checks back this up, since QIR carries no types to check again:

- **The verifier** (`quarz-lower`'s `verify.rs`) checks every function after each lowering pass and stops at the first violation, naming the pass, the function and the place, with its QIR. It checks the structure (targets, registers, lines and indices in range; handler-only instructions in their handlers; the marks of a pass absent before it), the value flow by reaching definitions with handler edges (words read and appended as they were made, no borrowed element updated, a `Resume` continuing what a `CatchAny` caught), the moves (no register read after its value moved out or its `Release`, on any path; a moved operand read once), the borrowed elements (as `mark_borrows` required, after it and register sharing), copy propagation, before and after (each `Release` kept, gone with a copy removed, or releasing the source that copy alone read: never another variable), and register sharing, before and after (no two registers live at once sharing a number, the two sides of a dropped move excepted; counted and non-counted registers apart, results apart from operands, clears kept). It is on in debug builds (`cargo test`) and off in release ones; `QUARZ_VERIFY_IR=0` or `1` overrides. The REPL, whose input goes through none of the passes, is checked right after lowering.
- **The interpreter checks the facts compiled code trusts** with `QUARZ_VERIFY=1`: what the checker's types say on an instruction (e.g. an `Array[Int]` or `Array[Float]`'s words and their index, an object's class at a field access and the field's word type, an `Int` or `Float` operator's operands, a parameter declared `Int` or `Float`) is checked before it is used, and a violated one, a bug in the checker or in lowering, stops the program with exit status 101, what was violated and a backtrace, not an exception a `rescue` could hide. `QUARZ_VERIFY=moves` also keeps a shadow of the registers a value moved out of or whose scope ended, and stops at a read of one. `cargo test` and `cargo run` set `moves`; unless it is `1` or `moves`, nothing is checked, at no cost per instruction (release benchmarks unchanged).

## 4. Interpreter

- **The interpreter executes QIR instructions directly**, without a separate bytecode. Registers hold tagged values: an `Int`, a `Float` or a `Bool` is not allocated, but carries its tag. Frequent operations (`Int`/`Float` arithmetic and comparisons, array element reads and appends, lengths, field access) have dedicated instructions.
- Because type information is available, there are none of the inline caches or guards that a dynamic-language interpreter needs. The target is Lua/LuaJIT-interpreter-class speed, roughly 3–10× Ruby (without YJIT).
- A baseline JIT (generating machine code from QIR on the fly) could be added in the future, but since the premise is "AOT for production," its priority is low.

## 5. Memory Management

We adopt **reference counting (RC) + in-place updates via uniqueness + cycle collection restricted to mutable objects**.

Today values are reference counted without atomic operations, and updates copy unless the reference is unique (§9). The shared bit with atomic counting and general reuse described below are not implemented: values cross to another thread only by copying (`Task.blocking`). Cycles are collected.

### Why Reference Counting

1. **In-place updates of immutable values**: an immutable value with a reference count of 1 can perform a "return a new value" operation destructively in place (Perceus, from Lean 4 / Koka). Quarz's "immutable by default yet fast" depends on this.
2. **Compatibility with AOT**: a tracing GC needs stack maps for native code (LLVM statepoints, etc.) or conservative scanning, which is a hard part of the implementation. RC needs neither, and the boundary with C FFI is simple.
3. **Deterministic release**: combined with `ensure`, resources like file handles can be released predictably.

### Details

- **Non-atomic counting is the default.** A value that crosses a task boundary (channel send, `Task.spawn` capture, `Atom`, constant) has its object graph traversed at that moment to set the "shared" bit, and thereafter uses atomic operations. Subgraphs that are already shared are not rescanned. Since immutable values do not change after being shared, no other synchronization is needed.
- **RC elision**: borrow inference (no `inc`/`dec` inserted for references that are merely passed as arguments and not retained), and cancellation of a `dec` immediately following an `inc`.
- **Reuse**: if an allocation of the same size follows immediately after a `dec` that hit exactly 0, the memory is reused (`with` on `data` and `Array#push` complete without allocating).
- **Cycle collection** (`quarz-vm`'s `cycles.rs`): an immutable value can only point to values older than itself at the time it is created, so immutable values alone cannot form a cycle: every cycle goes through something written after it was made, an object's field (a `var` field, or one `initialize` assigned once `self` was in use), a captured variable's slot in a heap frame, or a builder's contents. Those are the candidates: each is listed when it is made (an object only when one of its fields' declared types may lead back to it, which numbers, strings, symbols and collections of them cannot), in a list per thread whose place it keeps in its allocation's second word (unused by a local allocation), and leaves the list when freed or shared. Once as many candidates have been made as twice what the last collection found live (at least 10,000), the collector takes the local values reachable from the candidates and finds those whose counts are all accounted for by references from among them (CPython's algorithm: Bacon–Rajan's trial deletion would need to see the decrements, which compiled code makes inline); the rest, and what it reaches, is in use. The garbage is freed by emptying its candidates (fields and slots set to nil, contents taken), which leaves no cycle, and letting the counts do the rest. An object whose class defines `deinitialize` is queued first, intact, and freed by the next collection if it is still garbage once the method has run. The collector runs as a candidate is made, a point where every value in use is counted, so compiled code does nothing for it; what it cannot look into at that moment (a builder a native is borrowing) counts as in use. `QUARZ_NO_CYCLES=1` turns it off. A million two-object cycles and closures kept in a variable they capture took 834 MB and take 9 MB compiled (17 MB interpreted), with 23% more cycles compiled and 12% more interpreted (freeing what was leaked before included); a loop making as many candidates and no cycle takes 5% more cycles compiled and 2% more interpreted, and `bench/*` is unchanged (0.3% at most).
- **Small `Int` values, `Float` (when the type is static), `Bool`, `Nil`, `Symbol`** are not counted.
- **Deterministic release, and its limit**: a value is released when its last reference goes, so a file handle closes and a `deinitialize` (03-data-model §4) runs at a known point. Releasing at the last use would make that point earlier than the source suggests (a server socket used only for its port would close at once): a variable whose release may be observed lives to the end of its scope instead, the others still moving out at their last use.
- **Weak references** are not provided (the situations where they would be needed are cycles, which cycle collection resolves).

### Rejected Alternatives

- **Generational tracing GC (Go/Erlang/Ruby)**: fast allocation and no counting overhead, but loses points 1–3 above. Without in-place updates of immutable values, the cost of persistent data structures is paid every time.
- **Atomic RC at all times (Swift)**: simple, but the cost of atomic operations applies everywhere. The Lean 4 approach of "atomic only for shared subgraphs" fits Quarz, where task boundaries are explicit.

## 6. Native Code Generation

- The generator, written against a small instruction-builder trait, writes LLVM IR and compiles it with `clang -O2`, so the binary gets LLVM's optimizer and unwind tables (typed entries push no activation, since backtraces are recovered from the native stack; see §9). A second back end, Cranelift, generating machine code in-process for faster builds, was removed: the interpreter serves development, and keeping it cost a register-sharing policy of its own, a second declaration of every runtime call and about a third of the build tests' time.
- `Int` overflow checks use `llvm.sadd.with.overflow`, `Float` is unboxed, and small `data` instances are treated as structs via scalar replacement.
- Exceptions (`exit` among them, as `SystemExit`) and non-local exits (`break`/`return` out of blocks, an end of the program on a deadlock) are status codes that every compiled function returns and its callers test; unwind tables serve only to rebuild backtraces.
- Task stacks are reserved per task, and a switch is a swap of the stack pointer (`corosensei`).
- The output links the runtime (`libquarz_vm.a`) statically and the C library dynamically. Producing a shared library (`--shared`) is *planned*.

## 7. REPL and Development Experience

- `quarz repl` type-checks input and then runs it. An input with errors is discarded: what it declared, checked or assigned does not stay (the session goes back to where it was before it), except a file it required whose top level already ran, which cannot be undone and stays loaded; what its `static` statements printed was printed, and they run again when the input is entered again. `class` and `def` can be added interactively. Changing an existing definition, with the REPL recompiling and swapping "everything that uses that definition" (hot reload), is *planned*: today a redefinition is an error (§9). This is a REPL-only feature and does not affect program semantics. A class body's `static` statement ([14-metaprogramming.md](14-metaprogramming.md) §2) runs when its input is entered (or the file holding it is required), on the session's interpreter.
- Type errors are shown with Ruby-style location display, along with the expected and actual types. Narrowing hints ("`x` is `String?` here. You can narrow it with `if x`") are *planned*.
- The functions of each input are added to the interpreter's tables, which only grow (a failed input's stay there, unused): a task an earlier input left running, suspended in a call, keeps running the functions it was in while the next input's are loaded. The tables hand out their entries without borrowing them (`vm::entry`): an entry is never removed, replaced or moved, so a reference to one stays valid while the table lives.
- `quarz run --watch`, re-running on file changes, is *planned*.

## 8. Implementation Language and Structure

The implementation language is **Rust**. The front end, VM, and runtime are all written in Rust, and `cargo build` produces a single `quarz` binary.

### Why Rust

Listing what the Quarz implementation needs from the start, the decisive factor is how much of it is covered by the Rust ecosystem.

| Need | Provision in Rust |
|---|---|
| Stackful task switching | `corosensei` |
| Work-stealing scheduler, channels | `crossbeam` deques and synchronization primitives (planned: today the scheduler runs on one thread and needs neither) |
| Asynchronous IO | For sockets, epoll used directly on Linux (each socket registered once, edge-triggered) and `polling` (kqueue) elsewhere. Helper threads for whole-file, directory and metadata operations, name resolution, `connect`, child processes, and for filling or flushing the buffers of open `File`s and standard input. Writes to standard output and standard error are synchronous |
| Bignums, regular expressions, Unicode | `num-bigint` (or `rug`), `regex`, `unicode-*` |
| Persistent vector / HAMT | Written in-house, since in-place updates rely on RC uniqueness; `im`/`rpds` serve as references (planned: today collections are copy-on-write vectors and `indexmap` maps) |
| AST and type processing | `enum` and pattern matching |
| Native back end | LLVM through textual IR compiled by `clang` |

Other candidates considered:

- **C**: can be written in the same style as CRuby, but passed over because of the effort of vendoring the libraries in the table above and because the scheduler and channels — the parts most prone to bugs — would be written without safety nets.
- **OCaml (front end) + C (runtime)**: the best for writing a type checker, but the core of Quarz leans toward the runtime (RC, scheduler, in-place updates), and putting the type checker in a different language from that complicates the interpreter's startup path.
- **Zig**: suited to the runtime, but the language and standard library lack stability.
- **Write stage0 in Ruby and self-host early**: porting to Quarz would be easy, but every `quarz run` would type-check in Ruby, losing the fast startup of a development interpreter. Self-hosting is not required, and if done at all, it would come after the Rust implementation stabilizes.

### Guidelines for Writing in Rust

- **Confine `unsafe` to the runtime.** Tagged pointers, switching RC between non-atomic and atomic, and in-place updates lie outside Rust's ownership model; this part becomes "C written in Rust." `unsafe` goes only inside the runtime (`quarz-vm`; the code generator has one more), and the front end sees only safe APIs.
- **Hold the AST and types in arenas.** Do not build trees of `Rc<RefCell<_>>`; refer via `Vec` + `NodeId(u32)`/`TypeId(u32)` indices. This avoids fighting the borrow checker and simplifies conversion to QIR and cache serialization.
- **The parser is hand-written recursive descent.** Ruby-family grammars require a stateful lexer (`{` for block vs. hash, `name: Type` labels, heredocs, contextual keywords), so hand-writing suits it, as with Prism.
- **Split into crates to localize compile times.**

### Crate Layout

```
quarz/
  Cargo.toml          workspace
  crates/
    quarz-syntax      lexing, parsing, AST (with positions), error reporting
    quarz-types       name resolution, type checking, Shareable derivation, the check cache (§2)
    quarz-ir          QIR (the register-machine IR) and the run-time metadata (RtWorld)
    quarz-lower       checked AST → QIR
    quarz-vm          runtime (object model, RC, scheduler, channels, IO, natives) and the QIR interpreter;
                      also the static library compiled programs link against
    quarz-aot         QIR → machine code (LLVM through clang) and linking
    quarz-cli         quarz run / check / ir / build / repl
  std/                standard library (the part written in Quarz)
  docs/
  examples/
```

### Implementation Order

1. `quarz-syntax`: lexer, parser, AST. The goal is for `examples/` to parse.
2. `quarz-types`: name resolution and type checking. First monomorphic classes, methods, union types, and flow typing; then generics, `data`/`enum`, pattern exhaustiveness, and `extension`.
3. The minimal part of the runtime: object model and RC, `Int`/`String`/`Array`/`Hash`.
4. `quarz-vm`: QIR and the register VM. Run `examples/hello.qz` and `shapes.qz` with `quarz run`.
5. The concurrency part of the runtime: tasks, scheduler, channels, `Atom`, asynchronous IO. Run `wordcount.qz`, `pipeline.qz`, and `bank_actor.qz`.
6. Expand the standard library, REPL, separate checking and its cache (§2).
7. Native back end (LLVM).
8. Cogs ([10-cogs.md](10-cogs.md)), `fmt`, LSP.

## 9. The Current Implementation (v0.0.1)

What exists today differs from the plan above in a few deliberate ways; the plan still describes where the design is going.

- **Programs are lowered to QIR and interpreted by a register VM.** The checker annotates the tree with types, resolved call targets and variable slots; `quarz-lower` turns each method, block, constant initializer and file top level into a QIR function (`quarz ir FILE` prints them), the prelude's methods only once something lowered may call them (reachability by name, as for `quarz_ir::shake` below; a REPL input lowers what it newly reaches), which leaves a few dozen of its two hundred functions for most programs and takes a quarter off the start-up of `quarz run`; `quarz-vm` runs them. Locals captured by blocks live in heap frames, everything else in registers; keyword arguments are bound by the runtime and defaults evaluated in the callee's prologue; `break`/`return` out of blocks are status codes carried through the runtime; `ensure` is a handler block that catches every flow and resumes it (a `rescue` handler catches exceptions only: another flow goes past it to the `ensure` covering it), and a plain `return`/`break` that leaves an `ensure` region runs the body inline. `Int`/`Float` operators and generated field accessors bypass method dispatch, and so does `x.nil?` when none of the classes the receiver's static type allows (nor their subclasses, by class hierarchy analysis; a built-in value class has none) defines a `nil?` of its own: it is a test of the value (`IsNil`), which compiled code answers without a call (a loop over an `Int?` no longer goes through the runtime for it). The interpreter writes those operators' results and a field's value straight into the destination register: a value built aside was copied in with one wide load right after the narrower stores that built it, a load the store buffer cannot forward, which cost more than the operation (interpreted cycles: `objects` -32%, `dispatch` -24%, `loop` -27%, `collections` -18%, `fib` -14%). Every instruction carries its source line, so exceptions get a backtrace of `file:line:in name` frames (per task) and `__LINE__` works, interpreted or compiled.
- **Values are `Rc`-based.** Immutable collections are `Rc`-shared vectors and insertion-ordered maps, and updates use `Rc::make_mut`, which copies unless the reference is unique. Every empty array is one immortal allocation (an append copies it, which allocates as a first element would anyway: a million objects each holding an empty array took 223 MB, now 160 MB). An array of only `Int`s or only `Float`s stores machine words, an array of only objects (instances of classes, `data` types, variants, exceptions) their references, a word each (a million objects in an array: 8 MB less; compiled `dispatch`, over an array of shapes, 14% fewer cycles), and a hash whose keys and values are all `Int` an `Int`-to-`Int` table, in the interpreter as in compiled code. A value is two words (16 bytes): a tag byte, then the payload, at the next word or, for a short string, a `Bool` or a class, right after the tag; every heap payload is the runtime's one-word reference, which for a string, a byte string or an object finds the length in the allocation (a string's in the word before its counts, an object's in its layout), where a value had been three words to hold a fat pointer (a million short strings in an array: 36.3 MB -> 28.4 MB; a `Hash[String, Int]` of a million entries: 90.6 MB -> 77.2 MB; a million one-line lambdas: 537 MB -> 403 MB). A string of at most 14 bytes lives in the value itself (no allocation, no reference count: copying it is a copy of two words); a longer one is a shared `Rc<str>`; nothing observable depends on which (`==`, `equal?`, hashing and ordering compare the text). A value read for the last time moves rather than being copied: the receiver of `xs = xs.push(x)`, and an argument the caller does not read again, which the callee's parameter takes over, so `ys = add(ys, x)` with `def add(xs: Array[Int], v: Int) -> Array[Int] = xs.push(v)` updates in place as well. `QUARZ_COUNT_COPIES=1` reports at exit how many updates had to copy a shared collection, in the interpreter as in compiled code; a test checks that the loops meant to update in place copy nothing. The general Perceus-style reuse described in §5 is future work. The `Rc` is the runtime's own (`quarz-vm`'s `rc.rs`): a value that crosses to another task is marked shared, and only shared counts are updated atomically ([04-concurrency.md](04-concurrency.md) §7). A local allocation keeps its count in its first word; a shared one has 0 there and its count in the second word, so compiled code reads one word and bumps a nonzero count, or lowers one above 1, inline, calling the runtime otherwise. On the compiled `dispatch` and `objects` benchmarks (lengthened tenfold) that check costs 7–10% more instructions and no measurable cycles. An object (an instance of a class, `data` type, variant or exception) is one allocation of its header and exactly its fields: a `Vec2` took 104 bytes and a class with six fields 200, where every object had taken 160 (room for four fields), more going to a second allocation (a million one-field objects and 300,000 six-field ones: 344 MB -> 213 MB). A field declared `Int`, `Float` or `Bool` is its machine word, 8 bytes instead of a 16-byte value (`quarz_ir::field_slots` lays the fields out for the interpreter and compiled code alike): what the word cannot hold, nil before the field is assigned and, in an `Int` field, the smallest `Int`, is marked in the word (a NaN no arithmetic produces, for a `Float`) and kept aside, in a list the object points to (a word after the fields, in objects of classes with such fields). A `Vec2` now takes 80 bytes and the six-`Int`-field class 112 (those objects: 200 MB -> 156 MB; a million particles holding two `Vec2`s, a `Bool` and an `Int`: 253 MB -> 159 MB); compiled code reads and writes the words directly (an `Int` field's mark sends the read to the interpreter), and the compiled `objects` benchmark, lengthened, takes half the cycles; the interpreter's field reads, which dispatch on the field's kind, take a few instructions more (`objects` +5%). The header is two words after the counts (the layout, then the flags and the class): what an exception captured when it was raised is pointed at by a word after its fields, which only exceptions have (set once, atomically: the first raise wins; an exception made with other fields than its class's layout has keeps it in a table by the object's address instead), so a `Vec2` takes 56 bytes and the six-`Int`-field class 88 (a million `Vec2`s in an array: 121 MB -> 89 MB). A heap frame is one allocation too, its slots after a header of five words (the slot view compiled code reads, the slots' count, the parent and, for a frame that grew past them, which only a REPL's top level does, the vector its slots moved to), where it had kept room for eight slots in itself (a million one-line lambdas: 403 MB -> 262 MB; a call that makes a frame and a lambda, two million times: 4% fewer cycles interpreted, 7% compiled).
- **The allocator is mimalloc for blocks under 32 KiB and the system's `malloc` for larger ones**, in `quarz` and in compiled programs (the runtime library carries it): a reference-counted runtime frees as often as it allocates, mostly small blocks, which is the workload mimalloc was designed for (Koka and Lean), while glibc grows a large block in place or by remapping its pages where mimalloc copies it (an array or a string built up by appends: the compiled `collections` benchmark 20.5 ms with mimalloc alone, 16.3 ms so; a block's size, which comes back with it, says which allocator it belongs to). `QUARZ_ALLOC=system` selects the system's `malloc` instead, read once, at the first allocation; transparent huge pages, which mimalloc would ask for, are left off unless `QUARZ_THP=1` (as Go, the JVM and glibc's `malloc` leave them: the kernel zeroes them 2 MiB at a time, half a millisecond more for every process, and with large blocks from the system's allocator none of the benchmarks gains); building without the `mimalloc` feature (`cargo build --no-default-features`) leaves it out. Against the system's (glibc 2.36): `quarz run` of `p 1` 5.4 ms -> 4.9 ms, the interpreted benchmarks 1–5% fewer cycles (channel ping-pong 4%, spawn/await 5%); compiled ones 0–5% fewer; peak memory with many tasks 2–18% higher. That needs objects sized by their fields (below): when every object took the same size, the `objects` benchmark's short-lived `Vec2`s and its particles shared one size class, and mimalloc, which does not hand a freed block out again at once, scattered the particles among them (seven times the L1 misses, 5% more cycles than the system's).
- **Tasks are stackful coroutines (`corosensei`) run by worker threads (M:N): `QUARZ_THREADS` of them, by default as many as the CPUs the process may use (its affinity and cgroup quota, as Go's `GOMAXPROCS`).** The scheduler is cooperative (as Kotlin's): tasks switch at channel operations that wait, `sleep`, `await`, `Task.yield` and while waiting for I/O. Sockets wait on the scheduler's epoll/kqueue reactor; whole-file, directory and metadata operations, name resolution, child processes, and the reads and writes of an open `File` or standard input that its buffer cannot serve run on helper threads while only the calling task waits; `Task.blocking { }` runs its block in a second interpreter on another thread, only immutable values crossing over. Writes to standard output and standard error are synchronous. Each task reserves 16 MiB of virtual stack (256 MiB for the main task); exceeding it raises `SystemStackError`. Deadlock (every task blocked, no timers, no pending I/O) aborts the program with `DeadlockError`.
- **Worker threads.** Each worker has an interpreter of its own over the shared `Program` (what the loaded program derives, `Send + Sync`, checked at compile time) and `Global` (what the running program accumulates: the symbol table behind a read-write lock, of which each interpreter keeps local copies of the names it looked up; the constants, cells read without a lock once set, their initializer run once while other tasks wait; the enum variants without fields; the `at_exit` blocks and standard output), built on its own thread from the program image when a task is first placed there, and its own run queue, timers, epoll reactor and range of tags. A new task goes to each worker in turn and stays there, but for a `Task.timeout` block's, which runs on its caller's worker since the block is the caller's code (a coroutine and the native frames under it are bound to their thread); there is no work stealing yet. A task is known to the others as its worker and its number there: waking one on another worker puts it in that worker's inbox and wakes its reactor. A value that crosses from one task to another (sent on a channel, captured by `Task.spawn`, put in an `Atom`, returned by a task) is marked shared, with everything it refers to, and only shared counts are updated atomically (`rc.rs`: a shared allocation has 0 in the first word and its count in the second, so compiled code reads one word); constants, the top level's `self` and enum values are immortal, their counts never updated, so workers using them do not contend for a cache line. What tasks share keeps its state under locks: a channel's under a spin lock (a plain store to take while there is one worker), a task handle's in atomics and locks, an atom's value and an IO handle's state under mutexes; a socket is registered with the poller of each worker one of whose tasks waits on it. A deadlock is when every worker has nothing to run, no timer and no IO, with nothing on its way to one; the main worker reports it, with its own tasks. The program ends with its main task (or an `exit` in any task): the other workers stop, their tasks not unwound. The REPL and `Task.blocking`'s helper threads run one worker. Eight tasks computing `fib(27)` take 0.33 s on one worker and 0.12 s on four; the echo benchmark on four workers handles as many round trips as Go on four threads at 16 connections, and about 90% at 64 and 256 (bench/net/README.md). With one worker, 200,000 ping-pongs between two tasks cost 3% more instructions than before the workers came.
- **The REPL** (`quarz repl`) keeps declarations, variables and running tasks across inputs; each input is checked incrementally against the accumulated program. Redefining a class or method is an error (use a new name); the hot reload described in §7 is not implemented. `require` and `require_relative` work in the REPL and run the loaded file's top level once. Lines are edited with rustyline (Emacs or vi keys, `Ctrl-R` history search; `Ctrl-C` drops the input being typed, `Ctrl-D` exits); an input that lacks its end (an open block, bracket or string) goes on in the same entry, so a definition is edited and recalled from the history whole; the next line starts with as many spaces as the prompt is wide, part of the entry (rustyline shows no prompt there), so the code lines up, except inside a string, which the spaces would change. The history (1000 entries) is kept in `~/.quarz_history`. The entry is highlighted as it is typed, from the lexer's tokens (not with `NO_COLOR` set), and Tab completes names from what the session knows: local variables, top-level methods, keywords and constants; after a dot the methods of the receiver's type (a local variable's declared type, a class's own methods, a literal's class; any method when the type is not known), after `::` the constants of a class or module.
- **Cogs** ([10-cogs.md](10-cogs.md)). `quarz-cog` reads `Cog.toml` and `Cog.lock`, resolves versions by minimal version selection, mirrors each repository in the cache with the `git` command (fetching only the commits it needs), exports each locked commit's tree read-only and verifies it against the lock's content hash; `quarz-types` loads every file of each cog's `src/` (the dependencies first) and checks a library cog's files as the body of its root module, which is registered nowhere at the top level: each cog sees its dependencies by its manifest's keys, and a library does not see the application's names. A standard library module that a program names (`JSON`, `TCPSocket`) is loaded without `require`, in scripts and the REPL too.
- **`Bytes`, `Time` and the `json` library.** `Bytes` is an immutable byte sequence with `b"..."` literals, `Bytes::Builder`, `String#to_bytes`/`encode` and `Bytes#decode` (UTF-8, ASCII and ISO-8859-1). `Time` is a point in time with a UTC offset (`Time.now`/`utc`/`local`/`at`/`parse`/`iso8601`, `strftime`, arithmetic with `Duration`); `Time.monotonic` returns the monotonic clock as a `Duration`, and `require "time"` is accepted but not needed. `require "json"` gives `JSON.parse -> JSON::Value`, an enum with the variants `Null`, `Boolean`, `Integer`, `Number`, `Text`, `List` and `Map` (each carrying its value, with accessors such as `as_s`, `as_i?` and `[]`), `JSON.generate`/`pretty_generate` and `to_json`; a class customizes its JSON by defining `to_json -> String`. The parser and generator are native; the rest of the library is written in Quarz (`std/json.qz`).
- **`quarz build` compiles to a native executable.** `quarz-aot` translates every QIR function to machine code, with LLVM by default (the module is written as LLVM IR and compiled by `clang -O2`; `QUARZ_CLANG` names the compiler, `QUARZ_KEEP_IR` keeps the `.ll` next to the output): the generator is written against a small instruction-builder trait. Moves, immediates, branches and `Int`/`Float` arithmetic and comparisons (with overflow and division checks) are inlined; calls to methods that class hierarchy analysis proves are never overridden go straight to the native (`qz_call_static`, with the block if any) or, for a compiled body, directly to it: the caller lays the parameters out in its own frame (an unboxed number as a tag and a word) and builds the callee's activation in a stack buffer; when the callee needs neither a heap frame nor a method tag and gets no block, the activation is built, pushed on the call stack, torn down and popped inline (with the native-stack check), by the offsets `quarz_vm::layout` exports, and a program refuses to start on a runtime with another layout; otherwise the runtime does it (`qz_enter`/`qz_leave`); a method whose result is declared `Int`, `Float`, `Bool` or `Nil` (with positional parameters only, no block, no frame, nothing reading the argument list) also gets a *typed entry* (`qz_fn_N_t`) that takes the parameters and returns the result as machine values (a `Bool` as a byte, a `Nil` result as nothing; a `Bool` parameter is read into its variable once in the boxed body too, as an `Int` or `Float` one is), a parameter of any other type being lent: the caller passes its value's address and keeps it, releasing it after the call when that was its last use, and the callee counts it into its register (any other way out, an exception or a result that is not of the declared type, leaves a status in the runtime for the caller to read, so the normal return is a single register); with LLVM, when such a function can return without needing a frame (a part with only arithmetic, comparisons, copies and branches on unboxed values leading to a `return` of the declared type, as `tak`'s `return z if y >= x`), that part is compiled again as a separate entry function that callers call and LLVM inlines into them: leaving it (a call, an overflow, anything else) calls the full body with the same arguments, which runs the part again (it has no effects), so a call that returns at once costs a comparison and a branch at the call site, without a frame, a stack check or a call; with LLVM it pushes no activation at all (one is built, with its `self` cloned and its parameters boxed, only on the paths where the runtime needs it), because backtraces are recovered from the native stack: every compiled function carries unwind tables and the QIR line of each call as its DWARF line, the runtime walks the stack with the C unwinder when an exception is raised and maps the return addresses to functions and lines through a table the build extracts from the linked executable's symbols and line table into a section of its own (`.quarz_bt`) before stripping the executable of both, which with the standard library's debug information were three quarters of its size (`p 1`: 6.1 MB -> 1.6 MB; `QUARZ_NO_STRIP=1` keeps them, and the runtime then reads them directly), and merges those frames, by stack address, with the activations of interpreted and boxed frames (each activation records its own address, and the frames a task's coroutine stack holds are told apart by its range). A direct call uses the typed entry when the arguments are of the declared types, falling back to the boxed protocol otherwise (both that fallback and what follows a status other than a value are weighted cold, so that LLVM lays them out of the hot path's way: between its blocks, they had moved the hot code's alignment with every change to their size, the compiled `fib(32)` taking 11% more cycles when values became two words, and 28% fewer than that once they were out; `bench/fib.qz`, 21%); registers that only inline code writes have no nil written to their home at entry, nor those that may hold a heap value: the exit releases them under a mask, set per path, of the homes that hold one; the callee's result slot is set to nil once per function (every consumer leaves it so); the registers of an inlined callee, nil at its entry, get their nil written only where something reads the home (a read, a runtime call, a successor block), so an inlined call costs no stores for its locals; a call to a method that some class overrides is, when at most six classes can receive it and each runs a known small method, split by the lowering into exact class tests (a tag test and a class id comparison) leading to direct calls that the inliner copies in, the dispatched call staying as the fallback; otherwise it lays its arguments out as a direct call does, and `qz_enter_virtual` resolves it on the receiver's class (a class-by-method dispatch table, filled on first use, replaces the hash lookup) and builds the activation, the compiled body being called through the address it returns, or runs the call itself when the target has another shape. `yield` and constructors use dedicated entry points (a data type given all its fields is built in its allocation from the fields laid out in the caller's argument area); `x = x.push(v)` and `@items = @items.push(v)` move the collection out of the variable or field and update it in place when nothing else refers to it, the common `Array`/`Hash`/`Set` updates without even building an argument list; a `data` value that never escapes the function (built, read field by field, dropped) is not allocated at all, its field reads becoming reads of the constructor's argument registers; a field whose type is such a data type (all `Int`/`Float`/`Bool` fields, see 01-syntax §4) holds it in place, its physical fields laid out in the object (the lowering turns a read into a construction that scalar replacement removes, and a write into stores of the components), so a `Vec2` stored in a particle costs no allocation either; an array whose elements are all `Int` or all `Float` stores them unboxed (as machine words; the storage becomes boxed values when anything else is pushed, at most once per array), and so does a hash whose keys and values are all `Int` (an `Int`-to-`Int` table: lookups, `put`, `delete` and in-place updates work on it directly, other natives see it as boxed values), and an array's length, an element read by an in-range index (a word read and a tag for unboxed storage, a copy for boxed) and an append to an unshared array with room (`ArrayPush`, and `xs = xs.push(v)` on a local, a captured variable or a field) are done inline through the vector (whose word layout, with the storage kind, the runtime checks at start-up); `self`, parameters, captured variables (through the frame's slot view) and object fields (at fixed offsets after the object's header) are read and written inline, and a register known to hold an object (`self` in a method of a class whose instances are objects, an object whose field was just read or written, one that passed a class test) keeps the object's address in a variable, so its fields are read with no tag test and no reload of the register, and so does a register whose length or element was read, for its array, until it is written, appended to or has a method called on it (which may replace the allocation by a copy): a loop over an array tests its tag and reloads its register no more (lowering emits these instructions on arrays only); an array element a loop reads is borrowed when the array register holds the array wherever the element is still to be read (the loop keeps it to its end), so it is read without a count increment and dropped without a decrement (the interpreter copies it); reference counts are bumped and lowered inline, the runtime being called only to destroy the last reference; small methods (at most 40 instructions; no frame, no handlers, no blocks; two levels deep, so a recursive method like `tak` gets a copy of itself) are inlined into their callers on the QIR, with the callee's frames reconstructed in backtraces from an origin table; a copy of a register that is only read while both registers still hold the copied value is removed by copy propagation, and with it the copy's `Release` (the end of an inlined `self`'s scope: the source still holding the value, no deinitializer can run there; the copies that inlining and parameter binding produce were a reference-count increment and decrement each), and a class reference nothing reads (an inlined constructor's receiver) is not written, and a register read for the last time by a field store, an append, a data construction or a direct call's arguments is moved there rather than copied; the blocks of `times`, `upto`, `each`, `each_with_index`, `map`, `select`, `reject`, `reduce`, `count`, `any?` and `all?` on `Int`, `Array` and literal `Int` ranges are lowered in place as counted loops (so is `&:name` given for such a block, as a direct call of the method the checker resolved for the elements) when nothing nested captures their variables (`break`/`next` are jumps, the variables are registers, a block-local is nil again each iteration), so no closure is built and no call is made per element; over an `Array[Int]` or an `Array[Float]`, such a loop reads the elements as the machine words they are, with no check (`ArrayWords` makes the array store them so before the loop, copying it in the rare case that it does not, and `ArrayGetWord` loads one: summing an array costs 7 instructions an element rather than 20), over an array whose elements the checker types all objects (of a `data` type, an enum, an exception, or a class whose ancestors are `Object`, modules, exceptions and classes of the program: not `Object` or a module type, which built-in values may have), the element's allocation is taken from its payload with no tag test, into the object's variable; and the array `map` or `select` builds, when it is an `Array[Int]` or `Array[Float]`, stores words from the start (`ArrayNewWords`, with room for every element for `map`), appended to with only a room check (`ArrayPushWord`: nothing else refers to it); `==`/`!=` between two unboxed numbers of one kind is a machine comparison although `Int#==` takes an `Object`; and a constant or a copy nothing reads, into a register that never holds a counted value, is dropped; `xs[i]` with an `Int`, when it calls `Array#[]`, is an instruction of its own (`ArrayIndex`) whose index within range is read inline (into the unboxed variable for an `Array[Int]` or `Array[Float]` stored as words), the runtime taking negative indices and raising `IndexError`: a loop of such reads went from 190 instructions a read to 17; a register an array was made in, or appended to in place by `xs = xs.push(v)`, is known to hold one (its allocation in a variable), so the next append tests neither its tag nor reloads it; registers that a dataflow analysis proves hold an `Int` that fits a machine word, a `Float` or a `Bool` are unboxed into SSA variables, so arithmetic on them has no tag tests; the overload the lowering recorded for an operator (`Int#+(Int)`) gives the operand types, a parameter declared `Int`/`Float` is checked once when read, a field declared so is read straight into the unboxed variable (a `Float` field, which the checker's definite initialization guarantees holds a `Float`, with no check at all, and an unboxed `Float` stored into one writes the tag and the word with nothing to release; an `Int` field's word is compared with its mark, the smallest `Int` kept aside read by the runtime), `Int#to_f` on an unboxed `Int` is a conversion instruction, an operand of unknown state is checked once at run time, the static types making the check hold, and an overflow or a division by zero raises from the compiled code itself (`qz_raise`, through the function's handlers), so no compiled function hands its activation to an interpreter (a check that failed would be a compiler bug, raised as an internal `TypeError`); an unboxed register is written back to its boxed home only where memory is read (a runtime call, a handler, or a block that expects it boxed; an array's length, element read or append writes back only its own operands, on its runtime path), which a liveness analysis keeps to the registers still needed, and a call through a typed entry writes back only on its fallback paths; registers are initialized inline and released inline, a `return` releasing only the registers whose state allows a heap value; `==`/`!=` on `Int` and `Float` are inline comparisons; an in-place update whose result is not read (`xs = xs.push(v)` as a statement) is not stored; a constant initialized by a literal is that literal at its uses, a chain of `+` on strings (`a + b + c`) is built in one buffer like an interpolation, `b << "text #{x}"` on a `String::Builder` appends the interpolation to the builder without making a string or dispatching a call (straight into the builder when every interpolated value is a string, an integer, nil or a boolean, through a reused buffer otherwise, since a `to_s` may run code that touches the builder), a short string constant is written as the two words of its value, a longer one or a symbol is cloned from the function's pool by a direct runtime entry, and string interpolation has its own runtime entry; every other instruction calls the runtime's entry for its kind (`qz_op_*`, running the code the interpreter runs for it, `quarz_vm::ops`) on the compiled function's registers, its operands passed as arguments and, for lists (a call's arguments and keywords, an array literal's items, a type to check against), as words in the executable's data; exception and `ensure` routing is compiled. Natives that iterate (`each`, `map`, `select`, `times`) and `yield` prepare a block's activation once and reuse it per call. Common natives (`String#size`/`==`/`end_with?`/`upcase`/`+`, `String::Builder#<<`, `Array#size`/`[]`, `Hash#[]`/`key?`, …) have a by-reference version that takes the receiver and arguments straight from the registers, with no argument list and no copies, used by compiled calls, by the interpreter and by `&:name` procs (which cache the method found for the last receiver class, unless shared, since tasks on other workers may call a shared one at once, and which the iterating natives call without building an argument list); string interpolation, `upcase`, `+` and `Int#to_s` build their result in a reused buffer (integers by the runtime's own decimal conversion), so each costs at most one allocation, and a short result none. The executable embeds the serialized module (the runtime needs the class and method tables, and each function's constants; the functions' bodies are left out, `quarz_ir::Image`, but for what a body does with frames, which the runtime's analysis of a spawned block reads: the executable contains no QIR instruction, and no interpreter, which only `quarz run` and the REPL install, `Interp::install_interpreter`, so that the linker drops it with the code that would read instructions) and links `libquarz_vm.a` statically with the system `cc`, dropping the runtime code the program cannot reach (`--gc-sections`: a one-line program's executable 12.7 MB -> 10.6 MB; every native is a function of its own, named after its key, `qzn.Array#size`, and the executable refers only to those of the methods it keeps, through a table the build writes, the runtime's registry of all the natives being built only by what interprets: the same program's machine code and constants 4.69 MB -> 3.18 MB) and with the unwinder linked in (`-static-libgcc`: a shared library fewer to load), so the compiled program and `quarz run` share one runtime and behave identically (the test suite compiles every example and compares). At start-up a compiled program decodes its embedded module, but its methods: they are encoded apart and each decoded the first time it is needed, with what the runtime derives from every method (where its natives are in the program's tables; whether its parameters are positional only; the function a call can go straight to; its dispatch column) computed by the build and read in place (`quarz_vm::methods`: a one-line program's start-up 2.14M -> 1.34M instructions). The build also drops what the program cannot run before embedding the module (`quarz_ir::shake`: methods are reachable by name, from every call, symbol, `&:name`, operator and the few names the runtime calls by itself, since Quarz cannot call a method whose name is computed at run time, and a method found by name is kept only once its owner (or a descendant) can have values: a class the reachable code names or constructs, the classes of its literals, every exception, and the classes in the result and block types of a reachable native, with their descendants and variants (`RtMethod::makes`), so that `p 1` keeps 155 natives rather than 234 and no regular expression engine: 8.6 MB -> 6.1 MB; a dropped function keeps its id as an empty body that fails if it ever runs, and a dropped record is encoded as one byte; `QUARZ_NO_SHAKE=1` keeps everything), which also makes the build several times faster; the embedded module is decoded, the native tables are built with a fast hasher, and nothing is freed at exit. There is no `--release`/`--dev` distinction yet, and values other than local numbers stay boxed, so what remains between compiled Quarz and Go or Rust is the tagged, reference-counted value representation, heap allocation of every object and the call protocol of the calls that remain. Measurements against Go, Rust, Ruby and Spinel are in `bench/compare/README.md`.
- **Not implemented yet:** `quarz build --release`/`--dev`, FFI (`extern`), `Supervisor`, `Task#on_exit`, `Date`, `JSON.decode[T]` (type arguments do not exist at run time yet), `Bytes#pack`/`unpack`, `Encoding`, `Int32`/`Float32` and the other fixed-width numbers, `%W`-style literals. `String` and `Regexp` use Rust's `regex` crate, whose syntax differs from Onigmo in places (no look-behind, no back-references in patterns).
- **Small decisions made while implementing**, documented here so the other chapters stay as the design: a top-level `def` that does not use `self` (no `self`, no `super`, no call on the implicit receiver that passes it, in its body, blocks or parameter defaults) is called without its file's top-level object, the caller's `self` going in its place, which it never reads (so the call costs nothing more and may be inlined); one that does gets the object (`Inst::UnitSelf`); parameters after `*rest` are keyword-only (as after a bare `*`); `[]?` is a method name (`xs[i]?`); `x in pattern` is allowed inside argument lists; `[a, b] <=> [c, d]` on array literals is checked element-wise as tuples; a block with several parameters receiving one array or tuple spreads it over the parameters, as in Ruby; `Object` includes `Kernel`, so `puts` is a private method of every object; `IO` handles are `Shareable` (the runtime serializes access); the prelude declares built-ins with `native def`; `Comparable#clamp` returns the receiver or one of its bounds, typed `Self | T`; pattern variables bound in different `case/in` arms are separate variables; a `case/in` that misses an alternative of a union, a `data`, an `enum`, `Nil` or `Bool` is an error, while missing values of an open type such as `Int` is a warning and a run-time `NoMatchingPatternError`; `case/when` whose type tests cover the subject needs no `else`; `loop` without `break` has type `Nothing`; floats print the way Ruby prints them; `Hash` keys and `Set` members compare by `==` and `hash`, a class's own called from inside the tables' comparisons through the thread's runtime (`quarz-vm`'s `keys.rs`), what they raise kept and raised when the operation returns (03-data-model.md §6); when a subclass or enum variant overrides one overload of an overloaded method, calls resolved to the other overloads keep going to the superclass (the runtime dispatches by signature, not only by name).
